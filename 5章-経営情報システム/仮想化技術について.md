# 仮想化技術について

## 概要
仮想化技術は、物理的なハードウェアリソースを論理的に分割・統合し、複数の独立した仮想環境を作り出す技術です。これにより、リソースの効率的な活用、運用コストの削減、システムの柔軟性向上が実現できます。近年のクラウドコンピューティングの基盤技術として、その重要性はますます高まっています。

## 1. 基本概念・仕組み

### 仮想化の定義
- **定義**: 物理的なコンピュータリソース（CPU、メモリ、ストレージ、ネットワーク）を抽象化し、論理的なリソースとして提供する技術
- **動作原理**: 仮想化層（仮想化ソフトウェア）が物理リソースと仮想環境の間に入り、リソースの管理・割り当てを行う
- **特徴**: 
  - リソースの動的な割り当てが可能
  - 複数の仮想環境が同一物理マシン上で独立して動作
  - ハードウェアの違いを吸収し、移植性を向上

### 従来技術との関係
- **従来技術との違い**: 
  - 物理サーバー1台に1つのOSという制約からの解放
  - リソース利用率の大幅な改善（従来5-15% → 仮想化後60-80%）
- **改善点**: 
  - サーバー統合によるハードウェアコストの削減
  - 迅速なシステム構築・展開
  - 災害対策・事業継続性の向上
- **限界**: 
  - オーバーヘッドによる性能低下
  - 仮想化に適さないワークロードの存在

## 2. 種類・分類

### 仮想化の分類軸
仮想化技術は、抽象化のレベルや実装方式によって以下のように分類されます。

### ハイパーバイザ型（Type 1/Type 2）
**特徴:**
- ハードウェアを直接制御するソフトウェア層
- 複数の仮想マシン（VM）を管理
- 完全に独立したOS環境を提供

**Type 1（ベアメタル型）:**
```
[仮想マシン1] [仮想マシン2] [仮想マシン3]
    ↓             ↓             ↓
[    ハイパーバイザ（VMware ESXi、Hyper-V等）   ]
    ↓
[           物理ハードウェア              ]
```

**📊 具体的な計算例**
**例: VMware ESXiサーバーのリソース配分**
- 物理サーバー: CPU 32コア、メモリ 256GB、ストレージ 10TB
- VM1（Webサーバー）: CPU 4コア、メモリ 16GB、ストレージ 100GB
- VM2（DBサーバー）: CPU 8コア、メモリ 64GB、ストレージ 500GB
- VM3（開発環境）: CPU 2コア、メモリ 8GB、ストレージ 50GB

**ステップ1: CPU使用率の計算**
```
使用CPU = 4 + 8 + 2 = 14コア
CPU使用率 = 14 / 32 × 100 = 43.75%
```

**ステップ2: メモリ使用率の計算**
```
使用メモリ = 16 + 64 + 8 = 88GB
メモリ使用率 = 88 / 256 × 100 = 34.38%
```

**結果: リソースに余裕があり、さらに10-15台のVMを追加可能**

💡 **実際の現場では**: CPU、メモリのオーバーコミットを考慮し、物理リソースの1.5-2倍程度まで仮想リソースを割り当てることが一般的

**Type 2（ホスト型）:**
```
[仮想マシン1] [仮想マシン2] [仮想マシン3]
    ↓             ↓             ↓
[    ハイパーバイザ（VirtualBox、VMware Workstation等）   ]
    ↓
[        ホストOS（Windows、macOS、Linux等）        ]
    ↓
[           物理ハードウェア              ]
```

**特徴:**
- ホストOS上でアプリケーションとして動作
- 個人利用や開発環境での使用が主流
- 導入が容易で、既存環境への影響が少ない

**主な製品:**
- Oracle VirtualBox（無償）
- VMware Workstation（Windows/Linux）/ VMware Fusion（macOS）
- Parallels Desktop（macOS）
- Microsoft Virtual PC（旧製品）

**📊 具体的な計算例**
**例: 開発者のワークステーションでの仮想環境構築**
- ホストマシン: Windows 10、CPU 8コア、メモリ 32GB
- ホストOSの使用リソース: CPU 2コア相当、メモリ 8GB
- 利用可能リソース: CPU 6コア相当、メモリ 24GB

**ステップ1: 仮想マシンの構成**
```
VM1（Linux開発環境）: CPU 2コア、メモリ 8GB
VM2（Windows Server テスト）: CPU 2コア、メモリ 8GB
VM3（データベース環境）: CPU 2コア、メモリ 4GB
```

**ステップ2: リソース使用率の計算**
```
仮想マシンの合計CPU = 2 + 2 + 2 = 6コア
仮想マシンの合計メモリ = 8 + 8 + 4 = 20GB

CPU使用率 = (2 + 6) / 8 × 100 = 100%
メモリ使用率 = (8 + 20) / 32 × 100 = 87.5%
```

**結果: CPUはフル活用、メモリに若干の余裕あり**

💡 **実際の現場では**: 
- 開発・テスト環境として利用され、本番環境にはType 1を使用
- ホストOSの負荷も考慮し、リソースの70-80%程度の割り当てが推奨
- スナップショット機能を活用した開発環境の管理が一般的

**Type 1とType 2の比較:**
| 項目 | Type 1（ベアメタル型） | Type 2（ホスト型） |
|------|----------------------|------------------|
| 性能 | 高（オーバーヘッド小） | 中（ホストOS分のオーバーヘッド） |
| 管理性 | 専用管理ツール必要 | ホストOSから簡単に管理 |
| 用途 | 本番環境、データセンター | 開発環境、個人利用 |
| コスト | 高（専用ライセンス） | 低（無償版も存在） |
| 導入難易度 | 高（専門知識必要） | 低（一般的なソフトウェアと同様） |

### コンテナ型
**特徴:**
- OSカーネルを共有し、プロセスレベルで隔離
- 軽量で高速な起動・停止
- マイクロサービスアーキテクチャに最適

**アーキテクチャ:**
```
[コンテナ1] [コンテナ2] [コンテナ3]
    ↓          ↓          ↓
[   コンテナエンジン（Docker等）    ]
    ↓
[        ホストOS（Linux等）        ]
    ↓
[         物理ハードウェア          ]
```

**📊 具体的な計算例**
**例: Dockerコンテナのリソース制限設定**
- ホストマシン: CPU 8コア、メモリ 32GB
- コンテナA（Nginx）: CPU制限 0.5コア、メモリ制限 512MB
- コンテナB（Node.js）: CPU制限 2コア、メモリ制限 4GB
- コンテナC（Redis）: CPU制限 1コア、メモリ制限 2GB

**ステップ1: リソース制限の設定コマンド**
```bash
# コンテナAの起動
docker run -d --name nginx --cpus="0.5" --memory="512m" nginx:latest

# コンテナBの起動
docker run -d --name nodejs --cpus="2" --memory="4g" node:latest

# コンテナCの起動
docker run -d --name redis --cpus="1" --memory="2g" redis:latest
```

**ステップ2: 実際のリソース使用状況の確認**
```bash
docker stats --no-stream
# 出力例:
# NAME     CPU %   MEM USAGE / LIMIT
# nginx    12.5%   256MB / 512MB
# nodejs   45.2%   3.2GB / 4GB
# redis    25.0%   1.5GB / 2GB
```

💡 **実際の現場では**: Kubernetesを使用してコンテナのオーケストレーションを行い、自動スケーリングやロードバランシングを実現

### アプリケーション仮想化
**特徴:**
- 特定のアプリケーションのみを仮想化
- OSから独立した実行環境を提供
- 配布・管理の簡素化

**実装例:**
- Citrix Virtual Apps
- VMware ThinApp
- Microsoft App-V

### デスクトップ仮想化（VDI）
**特徴:**
- デスクトップ環境全体をサーバー側で実行
- シンクライアントからのアクセス
- セキュリティと管理性の向上

## 3. 詳細仕様・パラメータ

### ハイパーバイザの重要パラメータ
#### CPU仮想化設定
- **意味**: 物理CPUを仮想CPUにマッピングする方式
- **設定範囲**: 
  - vCPU数: 1-128（物理コア数に依存）
  - CPU予約: 0-100%
  - CPU制限: 0-無制限
- **影響**: パフォーマンスとリソース配分のバランス
- **推奨値**: 物理コア数の2-4倍までのvCPU総数

#### メモリ管理設定
- **意味**: 仮想マシンへのメモリ割り当て方式
- **設定範囲**: 
  - メモリサイズ: 512MB-6TB
  - メモリ予約: 0-100%
  - バルーニング: 有効/無効
- **影響**: メモリ使用効率とパフォーマンス
- **推奨値**: 実使用量の1.2倍程度を割り当て

### コンテナの重要パラメータ
#### リソース制限
- **CPU制限**: --cpus（コア数）、--cpu-shares（相対的な重み）
- **メモリ制限**: --memory（絶対値）、--memory-swap（スワップ含む）
- **I/O制限**: --device-read-bps、--device-write-bps

  web:
    image: nginx:latest

      - "80:80"

      - db_data:/var/lib/postgresql/data

#### 事例1: 楽天株式会社 - プライベートクラウド基盤

- **結果**: 物理サーバー数を80%削減、新規サービス立ち上げ時間を週単位から時間単位に短縮

- **適用方法**: Kubernetesを活用したコンテナ基盤への移行
- **結果**: 200以上のマイクロサービスを独立して開発・運用
- **効果**: デプロイ頻度が10倍に向上、障害の影響範囲を限定化

## 5. メリット・デメリット

### メリット
**1. コスト削減**
- **理由**: ハードウェアの集約によるTCO（総所有コスト）の削減
- **効果**: 
  - ハードウェアコスト: 50-70%削減
  - 電力・冷却コスト: 60-80%削減
  - 運用人件費: 30-50%削減
- **具体例**: 100台の物理サーバーを10台に集約し、年間1,000万円のコスト削減

**2. 運用効率の向上**
- **理由**: 自動化・標準化による管理負荷の軽減
- **効果**: 
  - プロビジョニング時間: 数日→数分
  - バックアップ・リストア: 自動化により90%の工数削減
- **具体例**: VMテンプレートにより、新規サーバー構築が10分で完了

**3. 柔軟性・拡張性**
- **理由**: リソースの動的な割り当てと変更が可能
- **効果**: ビジネス要求への迅速な対応
- **具体例**: 繁忙期のみリソースを増強し、閑散期は削減

### デメリット
**1. パフォーマンスオーバーヘッド**
- **理由**: 仮想化層による処理の追加
- **影響**: 
  - CPU: 5-15%の性能低下
  - I/O: 10-30%の性能低下（ストレージ仮想化使用時）
- **対策**: 
  - SR-IOV等のハードウェア支援機能の活用
  - パフォーマンスクリティカルなワークロードは物理環境で実行

**2. 複雑性の増加**
- **理由**: 管理レイヤーの追加、トラブルシューティングの難化
- **影響**: 
  - 初期導入コストの増加
  - 専門知識を持つ人材の必要性
- **対策**: 
  - 段階的な導入と十分な教育・トレーニング
  - 監視・管理ツールの充実

**3. ライセンスコスト**
- **理由**: 仮想化ソフトウェアのライセンス費用
- **影響**: 
  - VMware vSphere: 1ソケットあたり約50万円
  - Windows Server: 仮想化権利の追加購入が必要
- **対策**: 
  - オープンソース（KVM、Xen）の活用
  - ライセンス体系を考慮した設計

### 適用判断フローチャート
1. **異なるOSの混在が必要か？** 
   - Yes → 次の判断へ
   - No → 判断3へ

2. **本番環境での利用か？**
   - Yes → Type 1ハイパーバイザ（高性能・高信頼性）
   - No → Type 2ハイパーバイザ（簡単導入・開発向け）

3. **完全な環境分離が必要か？**
   - Yes → 判断2へ（ハイパーバイザ選択）
   - No → 次の判断へ

4. **マイクロサービス・CI/CDでの利用か？**
   - Yes → コンテナ型
   - No → 次の判断へ

5. **特定アプリケーションの配布・管理が主目的か？**
   - Yes → アプリケーション仮想化
   - No → 要件の再検討

## 8. 理解度確認クイズ（4択問題20問）

### 問題1
仮想化技術の基本的な目的として最も適切なものはどれか？

- A) ハードウェアの性能を向上させること
- B) 物理リソースを論理的に分割・統合して効率的に利用すること
- C) ソフトウェアのバグを自動的に修正すること
- D) ネットワークの通信速度を高速化すること

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
仮想化技術の基本的な目的は、物理的なハードウェアリソースを論理的に分割・統合し、効率的に利用することです。<br>
<br>
Aが間違いの理由：仮想化はハードウェアの性能を向上させるのではなく、むしろオーバーヘッドにより若干の性能低下が生じます<br>
Cが間違いの理由：仮想化技術はバグ修正とは関係ありません<br>
Dが間違いの理由：仮想化技術は直接的にネットワーク速度を向上させるものではありません
</details>

### 問題2
Type 1ハイパーバイザ（ベアメタル型）の特徴として正しいものはどれか？

- A) ホストOS上で動作し、管理が容易である
- B) ハードウェア上で直接動作し、高いパフォーマンスを実現する
- C) コンテナ技術の一種である
- D) アプリケーションレベルでのみ仮想化を行う

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
Type 1ハイパーバイザは物理ハードウェア上で直接動作するため、ホストOSのオーバーヘッドがなく、高いパフォーマンスを実現します。<br>
<br>
Aが間違いの理由：これはType 2ハイパーバイザの特徴です<br>
Cが間違いの理由：ハイパーバイザとコンテナは異なる仮想化技術です<br>
Dが間違いの理由：ハイパーバイザはOS全体を仮想化します
</details>

### 問題3
コンテナ技術の最大の特徴は何か？

- A) 完全に独立したOS環境を提供する
- B) OSカーネルを共有し、軽量で高速な起動を実現する
- C) Windows上でLinuxを動作させることができる
- D) ハードウェアレベルでの仮想化を行う

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
コンテナ技術はホストOSのカーネルを共有することで、軽量化と高速な起動・停止を実現しています。<br>
<br>
Aが間違いの理由：完全に独立したOS環境はハイパーバイザ型の特徴です<br>
Cが間違いの理由：コンテナは同一OS系統でのみ動作します（LinuxコンテナはLinux上でのみ動作）<br>
Dが間違いの理由：コンテナはOSレベルでの仮想化であり、ハードウェアレベルではありません
</details>

### 問題4
仮想化におけるCPUオーバーコミットとは何を指すか？

- A) 物理CPUの性能を向上させる技術
- B) 物理CPUコア数を超えてvCPUを割り当てること
- C) CPUの故障を防ぐ技術
- D) CPUの消費電力を削減する技術

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
CPUオーバーコミットは、物理的なCPUコア数を超えて仮想CPU（vCPU）を割り当てる技術です。多くのVMが常時100%のCPUを使用しないことを前提に、リソースを効率的に活用します。<br>
<br>
Aが間違いの理由：オーバーコミットは性能向上ではなく、リソースの効率的な配分を目的とします<br>
Cが間違いの理由：故障防止とは関係ありません<br>
Dが間違いの理由：直接的な省電力技術ではありません
</details>

### 問題5
仮想マシンのライブマイグレーションとは何か？

- A) 仮想マシンを停止してから別のホストに移動すること
- B) 仮想マシンを稼働させたまま別のホストに移動すること
- C) 仮想マシンのバックアップを取ること

## 9. 専門用語集

このスライドで使用された技術用語について、アルファベット順・50音順で解説します。

### アルファベット

**API (Application Programming Interface)**
- **読み方**: エーピーアイ
- **意味**: アプリケーション間でデータや機能をやり取りするためのインターフェース仕様
- **関連用語**: REST API、マイクロサービス

**CI/CD (Continuous Integration/Continuous Delivery)**
- **読み方**: シーアイ・シーディー
- **意味**: 継続的インテグレーション/継続的デリバリー。コードの自動ビルド、テスト、デプロイを行う開発手法
- **関連用語**: DevOps、自動化

**CPU (Central Processing Unit)**
- **読み方**: シーピーユー
- **意味**: コンピュータの中央処理装置。仮想化では物理CPUを論理的に分割してvCPUとして提供
- **関連用語**: vCPU、コア、スレッド

**Docker**
- **読み方**: ドッカー
- **意味**: コンテナ型仮想化を実現するプラットフォーム。アプリケーションをコンテナとしてパッケージ化
- **関連用語**: コンテナ、イメージ、Dockerfile

**ESXi**
- **読み方**: イーエスエックスアイ
- **意味**: VMware社のType 1ハイパーバイザ。企業向け仮想化基盤として広く利用
- **関連用語**: vSphere、VMware、ハイパーバイザ

**Hyper-V**
- **読み方**: ハイパーブイ
- **意味**: Microsoft社のハイパーバイザ。Windows Serverに標準搭載
- **関連用語**: Windows Server、仮想化

**IaaS (Infrastructure as a Service)**
- **読み方**: イアース、アイアース
- **意味**: インフラをサービスとして提供するクラウドサービスモデル
- **関連用語**: PaaS、SaaS、クラウド

**IOPS (Input/Output Per Second)**
- **読み方**: アイオーピーエス
- **意味**: 1秒あたりの入出力操作数。ストレージ性能の指標
- **関連用語**: スループット、レイテンシ

**KVM (Kernel-based Virtual Machine)**
- **読み方**: ケーブイエム
- **意味**: Linuxカーネルに統合されたオープンソースのハイパーバイザ
- **関連用語**: QEMU、libvirt、オープンソース

**Kubernetes**
- **読み方**: クバネティス、クーべネティス
- **意味**: コンテナオーケストレーションプラットフォーム。複数のコンテナを管理・自動化
- **関連用語**: K8s、Pod、Service

**OpenStack**
- **読み方**: オープンスタック
- **意味**: オープンソースのクラウド基盤ソフトウェア。IaaSを構築可能
- **関連用語**: Nova、Neutron、プライベートクラウド

**Pod**
- **読み方**: ポッド
- **意味**: Kubernetesにおける最小のデプロイ単位。1つ以上のコンテナをグループ化
- **関連用語**: Kubernetes、コンテナ、Deployment

**QEMU**
- **読み方**: キューエミュー
- **意味**: オープンソースのマシンエミュレータ。KVMと組み合わせて使用
- **関連用語**: KVM、エミュレーション

**SR-IOV (Single Root I/O Virtualization)**
- **読み方**: エスアール・アイオーブイ
- **意味**: 物理デバイスを仮想的に分割し、VMから直接アクセス可能にする技術
- **関連用語**: PCIパススルー、I/O仮想化

**TCO (Total Cost of Ownership)**
- **読み方**: ティーシーオー
- **意味**: 総所有コスト。初期投資から運用・廃棄までの全コスト
- **関連用語**: ROI、コスト削減

**vCPU (Virtual CPU)**
- **読み方**: ブイシーピーユー
- **意味**: 仮想CPU。物理CPUを論理的に分割したもの
- **関連用語**: CPU、オーバーコミット

**VDI (Virtual Desktop Infrastructure)**
- **読み方**: ブイディーアイ
- **意味**: 仮想デスクトップ基盤。デスクトップ環境を仮想化して提供
- **関連用語**: シンクライアント、リモートデスクトップ

**VM (Virtual Machine)**
- **読み方**: ブイエム
- **意味**: 仮想マシン。物理マシン上で動作する論理的なコンピュータ
- **関連用語**: ゲストOS、ハイパーバイザ

**VMware**
- **読み方**: ブイエムウェア
- **意味**: 仮想化ソフトウェアの大手ベンダー。vSphereなどを提供
- **関連用語**: ESXi、vSphere、vCenter

**WebAssembly (WASM)**
- **読み方**: ウェブアセンブリ、ワズム
- **意味**: ウェブブラウザで動作する低レベルのバイナリ形式。サーバーサイドでも利用可能
- **関連用語**: サーバーレス、エッジコンピューティング

### あ行

**オーケストレーション**
- **読み方**: おーけすとれーしょん
- **意味**: 複数のコンテナやサービスを自動的に管理・調整すること
- **関連用語**: Kubernetes、Docker Swarm、自動化

**オーバーコミット**
- **読み方**: おーばーこみっと
- **意味**: 物理リソースを超えて仮想リソースを割り当てること
- **関連用語**: リソース管理、CPU、メモリ

### か行

**仮想化**
- **読み方**: かそうか

- **関連用語**: 抽象化、論理化

**仮想マシン**
- **読み方**: かそうましん
- **意味**: ソフトウェアで実装された仮想的なコンピュータ
- **関連用語**: VM、ゲストOS

**コンテナ**
- **読み方**: こんてな
- **意味**: アプリケーションとその実行環境をパッケージ化したもの
- **関連用語**: Docker、イメージ、軽量仮想化

**コンテナイメージ**
- **読み方**: こんてないめーじ
- **意味**: コンテナの実行に必要なファイルシステムとメタデータをパッケージ化したもの
- **関連用語**: Dockerfile、レイヤー、レジストリ

### は行

- **読み方**: はいぱーばいざ

- **関連用語**: Type 1、Type 2、VMM

**バルーニング**
- **読み方**: ばるーにんぐ

- **関連用語**: メモリ管理、動的割り当て

**プロビジョニング**
- **読み方**: ぷろびじょにんぐ

- **関連用語**: デプロイ、自動化

**ベアメタル**
- **読み方**: べあめたる
- **意味**: OSやソフトウェアがインストールされていない物理ハードウェア
- **関連用語**: 物理サーバー、Type 1ハイパーバイザ

**ホストOS**
- **読み方**: ほすとおーえす
- **意味**: Type 2ハイパーバイザ（ホスト型）が動作する基盤となるOS。Windows、macOS、Linuxなどの汎用OSがホストOSとなり、その上で仮想化ソフトウェアが動作する
- **関連用語**: ゲストOS、Type 2ハイパーバイザ、ホスト型仮想化

**ホスト型仮想化**
- **読み方**: ほすとがたかそうか
- **意味**: Type 2ハイパーバイザとも呼ばれる仮想化方式。既存のOS上でアプリケーションとして動作する仮想化ソフトウェアを使用する方式
- **関連用語**: Type 2ハイパーバイザ、VirtualBox、VMware Workstation
