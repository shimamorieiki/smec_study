# 開発モデルについて

## 概要
ソフトウェア開発モデルは、ソフトウェア開発プロジェクトを計画・実行・管理するための体系的なアプローチです。各モデルは異なる特性を持ち、プロジェクトの性質や要求に応じて選択されます。本資料では、主要な開発モデルであるウォーターフォール、スパイラル、インクリメンタル、そして特にアジャイル開発について、その特徴と各種手法を詳しく解説します。

## 1. 開発モデルの基本概念

### ソフトウェア開発ライフサイクル（SDLC）
- **定義**: ソフトウェアの構想から廃棄までの全過程を体系化したもの
- **特徴**: 各開発モデルはSDLCの実装方法の違いを表す
- **重要性**: プロジェクトの成功率向上と品質保証の基盤

### 開発モデル選択の重要性
- **定義**: プロジェクトの特性に最適な開発手法を選ぶプロセス
- **特徴**: プロジェクトの成否を左右する重要な意思決定
- **重要性**: コスト、品質、納期のバランスを最適化

## 2. 主要開発モデルの分類

### 伝統的モデルと反復的モデル
開発モデルは大きく2つのカテゴリーに分類されます。

### 伝統的（計画駆動型）モデル
| 項目 | 内容 |
|------|------|
| 特徴 | 事前の詳細な計画と文書化を重視 |
| 適用範囲 | 要求が明確で変更が少ないプロジェクト |
| 代表例 | ウォーターフォールモデル |

### 反復的・インクリメンタルモデル
| 項目 | 内容 |
|------|------|
| 特徴 | 小さな単位で開発を繰り返す |
| 適用範囲 | 要求が不明確または変更が多いプロジェクト |
| 代表例 | スパイラル、インクリメンタル、アジャイル |

## 3. ウォーターフォールモデル

### 基本概念
**ウォーターフォールモデル**は、1970年にWinston W. Royceが提唱した最も伝統的な開発モデルです。上流工程から下流工程へ、滝が流れ落ちるように一方向に進む開発手法です。

### 開発フェーズ
1. **要求定義フェーズ**
   - システムの機能要求・非機能要求を明確化
   - ステークホルダーとの合意形成
   - 要求仕様書の作成

2. **設計フェーズ**
   - 基本設計（外部設計）：システムの全体構成
   - 詳細設計（内部設計）：モジュール単位の設計
   - データベース設計、画面設計、帳票設計

3. **実装フェーズ**
   - プログラミング作業
   - 単体テストの実施
   - コードレビュー

4. **テストフェーズ**
   - 結合テスト：モジュール間の連携確認
   - システムテスト：システム全体の動作確認
   - 受入テスト：ユーザー要求との適合性確認

5. **運用・保守フェーズ**
   - システムの本番稼働
   - 不具合対応と機能改善
   - パフォーマンスチューニング

### メリット・デメリット

**メリット:**
- **計画の立てやすさ**: 各フェーズの成果物が明確
- **進捗管理の容易さ**: マイルストーンが明確
- **品質保証**: 各フェーズでの検証が徹底的

**デメリット:**
- **柔軟性の欠如**: 後戻りが困難
- **リスクの遅延発見**: 問題が後工程で発覚
- **ユーザーフィードバックの遅れ**: 最終段階まで動作確認不可

### 適用が適している場面
- 要求が明確で変更が少ない
- 規模が大きく、長期的なプロジェクト
- 規制の厳しい業界（金融、医療、航空宇宙）

## 4. スパイラルモデル

### 基本概念
**スパイラルモデル**は、1986年にBarry Boehmが提唱したリスク駆動型の開発モデルです。開発を螺旋状に繰り返しながら、段階的にシステムを完成させていきます。

### 4つの基本活動
1. **目標設定**
   - 各反復の目標を明確化
   - 制約条件の特定
   - 代替案の検討

2. **リスク分析**
   - 技術的リスクの評価
   - コストリスクの分析
   - スケジュールリスクの検討
   - プロトタイプによる検証

3. **開発と検証**
   - 選択した代替案の実装
   - テストの実施
   - 品質の確認

4. **計画**
   - 次の反復の計画立案
   - レビューの実施
   - ステークホルダーとの合意

### 実装例
```
第1サイクル：概念実証（PoC）
- 目標：技術的実現可能性の確認
- リスク分析：主要技術リスクの特定
- 開発：基本機能のプロトタイプ
- 計画：本格開発への移行判断

第2サイクル：基本機能開発
- 目標：コア機能の実装
- リスク分析：アーキテクチャリスクの評価
- 開発：基本機能の実装とテスト
- 計画：追加機能の優先順位付け

第3サイクル：機能拡張
- 目標：付加価値機能の追加
- リスク分析：統合リスクの評価
- 開発：全機能の統合とテスト
- 計画：リリース準備
```

### メリット・デメリット

**メリット:**
- **リスク管理**: 早期のリスク特定と対策
- **柔軟性**: 各サイクルでの方向修正が可能
- **品質向上**: 継続的な検証による品質確保

**デメリット:**
- **複雑性**: 管理が複雑
- **コスト**: リスク分析に時間とコストがかかる
- **専門性**: リスク管理の専門知識が必要

## 5. インクリメンタルモデル

### 基本概念
**インクリメンタルモデル**は、システムを複数の増分（インクリメント）に分割し、各増分を順次開発・リリースしていく手法です。

### 開発プロセス
1. **全体計画**
   - システム全体の要求分析
   - インクリメントへの分割
   - 優先順位の決定

2. **インクリメント開発**
   - 各インクリメントの詳細設計
   - 実装とテスト
   - 部分的なリリース

3. **統合**
   - 既存インクリメントとの統合
   - 回帰テストの実施
   - システム全体の検証

### 📊 具体的な実装例
**例: ECサイトの開発**

**インクリメント1: 基本機能（2ヶ月）**
- 商品検索・表示機能
- ショッピングカート機能
- 基本的な注文機能

**インクリメント2: ユーザー管理（1.5ヶ月）**
- ユーザー登録・ログイン
- マイページ機能
- 注文履歴管理

**インクリメント3: 決済機能（2ヶ月）**
- クレジットカード決済
- 電子マネー決済
- ポイント機能

**インクリメント4: 高度な機能（1.5ヶ月）**
- レコメンド機能
- レビュー・評価機能
- 在庫管理連携

💡 **実際の現場では**: 各インクリメントの完了時に部分的にリリースし、ユーザーフィードバックを次のインクリメントに反映させます。

### メリット・デメリット

**メリット:**
- **早期価値提供**: 部分的でも早期に利用可能
- **リスク分散**: 問題の早期発見
- **柔軟な対応**: フィードバックの反映が容易

**デメリット:**
- **設計の複雑性**: 全体アーキテクチャの考慮が必要
- **統合の手間**: インクリメント間の整合性確保
- **計画の難しさ**: 適切な分割が困難

## 6. アジャイル開発

### 基本概念
**アジャイル開発**は、2001年に発表された「アジャイルソフトウェア開発宣言」に基づく、反復的で柔軟な開発手法の総称です。

### アジャイル宣言の4つの価値
1. **プロセスやツールよりも個人と対話を**
2. **包括的なドキュメントよりも動くソフトウェアを**
3. **契約交渉よりも顧客との協調を**
4. **計画に従うことよりも変化への対応を**

### アジャイルの12の原則
1. 顧客満足を最優先し、価値のあるソフトウェアを早く継続的に提供
2. 要求の変更はたとえ開発の後期であっても歓迎
3. 動くソフトウェアを、2-3週間から2-3ヶ月という短い期間でリリース
4. ビジネス側の人と開発者は、プロジェクトを通して日々一緒に働く
5. 意欲に満ちた人々を集めてプロジェクトを構成
6. 情報を伝える最も効率的で効果的な方法はフェイス・トゥ・フェイスで話すこと
7. 動くソフトウェアこそが進捗の最も重要な尺度
8. アジャイル・プロセスは持続可能な開発を促進
9. 技術的卓越性と優れた設計に対する不断の注意が機敏さを高める
10. シンプルさ（ムダなく作れる量を最大限にする技術）が本質
11. 最良のアーキテクチャ・要求・設計は、自己組織的なチームから生み出される
12. チームがもっと効率を高めることができるかを定期的に振り返り、それに基づいて自分たちのやり方を最適に調整

## 7. アジャイル開発の主要手法

### 7.1 スクラム（Scrum）

**基本概念:**
最も広く採用されているアジャイル手法。3つの役割、5つのイベント、3つの成果物で構成されます。

**3つの役割:**
1. **プロダクトオーナー（PO）**
   - プロダクトバックログの管理
   - ビジネス価値の最大化
   - ステークホルダーとの調整

2. **スクラムマスター（SM）**
   - スクラムプロセスの促進
   - 障害の除去
   - チームの自己組織化支援

3. **開発チーム**
   - 実際の開発作業
   - 自己組織的なチーム運営
   - クロスファンクショナルなスキル

**5つのイベント:**
1. **スプリント**: 1-4週間の開発期間
2. **スプリントプランニング**: スプリントの計画
3. **デイリースクラム**: 毎日15分の進捗確認
4. **スプリントレビュー**: 成果物のデモ
5. **スプリントレトロスペクティブ**: 振り返りと改善

**3つの成果物:**
1. **プロダクトバックログ**: 要求事項のリスト
2. **スプリントバックログ**: スプリントで実施する作業
3. **インクリメント**: 完成した成果物

### 7.2 エクストリームプログラミング（XP）

**基本概念:**
Kent Beckが提唱した、プログラミングに焦点を当てたアジャイル手法。

**5つの価値:**
1. **コミュニケーション**: 頻繁な対話
2. **シンプリシティ**: 最もシンプルな解決策
3. **フィードバック**: 早期かつ頻繁なフィードバック
4. **勇気**: 変更を恐れない
5. **リスペクト**: チームメンバーへの敬意

**主要プラクティス:**
- **ペアプログラミング**: 2人1組でのコーディング
- **テスト駆動開発（TDD）**: テストを先に書く
- **継続的インテグレーション**: 頻繁な統合
- **リファクタリング**: コードの継続的改善
- **小規模リリース**: 頻繁なリリース
- **コーディング規約**: 統一されたコーディングスタイル

### 7.3 カンバン

**基本概念:**
トヨタ生産方式から派生した、視覚的な作業管理手法。

**主要原則:**
1. **作業の可視化**: カンバンボードの使用
2. **WIP（Work In Progress）制限**: 同時進行作業の制限
3. **フローの管理**: ボトルネックの特定と解消
4. **明示的なポリシー**: ルールの明文化
5. **継続的改善**: データに基づく改善

**カンバンボードの例:**
```
| To Do | In Progress (3) | Review (2) | Done |
|-------|----------------|------------|------|
| Task A | Task D        | Task G     | Task J |
| Task B | Task E        | Task H     | Task K |
| Task C | Task F        |            | Task L |
```

### 7.4 リーンソフトウェア開発

**基本概念:**
トヨタ生産方式の原則をソフトウェア開発に適用。

**7つの原則:**
1. **無駄を排除する**: 不要な機能、待ち時間、手戻りの削減
2. **品質を作り込む**: 最初から品質を確保
3. **知識を創造する**: 継続的な学習
4. **決定を遅らせる**: 最後の責任ある瞬間まで待つ
5. **速く提供する**: 短いサイクルタイム
6. **人を尊重する**: チームの自律性
7. **全体を最適化する**: 部分最適化を避ける

### 7.5 フィーチャー駆動開発（FDD）

**基本概念:**
機能（フィーチャー）を中心とした反復的開発手法。

**5つのプロセス:**
1. **全体モデルの開発**: ドメインモデルの作成
2. **フィーチャーリストの作成**: 機能の洗い出し
3. **フィーチャーごとの計画**: 開発順序の決定
4. **フィーチャーごとの設計**: 詳細設計
5. **フィーチャーごとの構築**: 実装とテスト

**フィーチャーの定義:**
「<action> the <result> <by|for|of|to> a(n) <object>」
例：「Calculate the total price for a shopping cart」

### 7.6 クリスタル

**基本概念:**
Alistair Cockburnが提唱した、プロジェクトの規模と重要度に応じて手法を調整するアジャイルファミリー。

**種類:**
- **Crystal Clear**: 6人以下のチーム
- **Crystal Yellow**: 7-20人のチーム
- **Crystal Orange**: 21-40人のチーム
- **Crystal Red**: 41-80人のチーム

**共通原則:**
1. 頻繁なデリバリー
2. 振り返りによる改善
3. オスモティックコミュニケーション（浸透的コミュニケーション）
4. 個人の安全
5. フォーカス
6. 専門家へのアクセス
7. 技術的環境

### 7.7 動的システム開発手法（DSDM）

**基本概念:**
ビジネス価値の早期提供に焦点を当てたアジャイル手法。

**8つの原則:**
1. ビジネスニーズに焦点を当てる
2. 時間通りにデリバリーする
3. 協調する
4. 品質を決して妥協しない
5. 堅固な基盤から段階的に構築する
6. 反復的に開発する
7. 明確かつ継続的にコミュニケーションする
8. コントロールを実証する

**フェーズ:**
1. **実現可能性調査**: プロジェクトの実現可能性評価
2. **ビジネス調査**: 要求の理解
3. **機能モデル反復**: プロトタイプ開発
4. **設計と構築反復**: システム構築
5. **実装**: 本番環境への展開

### 7.8 適応型ソフトウェア開発（ASD）

**基本概念:**
Jim Highsmithが提唱した、複雑適応系理論に基づくアジャイル手法。

**3つのフェーズ:**
1. **推測（Speculate）**: 初期計画と適応的サイクル計画
2. **協調（Collaborate）**: チームワークと知識共有
3. **学習（Learn）**: 品質レビューと振り返り

**特徴:**
- 変化を前提とした計画
- 創発的な秩序
- 継続的な適応

## 8. 開発モデルの比較と選択指針

### 各モデルの比較表
| 観点 | ウォーターフォール | スパイラル | インクリメンタル | アジャイル |
|------|-------------------|-----------|----------------|-----------|
| 要求の明確さ | 必須 | 中程度 | 中程度 | 不要 |
| 変更への対応 | 困難 | 可能 | 可能 | 容易 |
| リスク管理 | 低い | 高い | 中程度 | 中程度 |
| 顧客関与 | 初期と最終 | 各サイクル | 各インクリメント | 継続的 |
| ドキュメント | 詳細 | 中程度 | 中程度 | 最小限 |
| 予測可能性 | 高い | 中程度 | 中程度 | 低い |

### 選択基準フローチャート
1. **要求は明確で変更が少ない？**
   - Yes → ウォーターフォールモデル
   - No → 次の判断へ

2. **リスクが高く、大規模なプロジェクト？**
   - Yes → スパイラルモデル
   - No → 次の判断へ

3. **早期に部分的な価値提供が必要？**
   - Yes → インクリメンタルモデル
   - No → アジャイル開発

4. **アジャイル手法の選択**
   - チーム規模6人以下 → Crystal ClearまたはXP
   - 明確な役割分担が必要 → スクラム
   - 継続的なフロー管理 → カンバン
   - ビジネス価値重視 → DSDM

## 9. 実務上の注意点

### 開発モデル導入時の重要ポイント
- **組織文化との適合性**: 既存の文化に合ったモデル選択
- **チームの成熟度**: スキルレベルに応じた選択
- **ステークホルダーの理解**: 関係者への説明と合意
- **段階的導入**: パイロットプロジェクトからの開始
- **継続的改善**: 定期的な振り返りと調整

### よくある誤解・トラブル
- **誤解1**: 「アジャイルは計画不要」→ 正解：適応的な計画が必要
- **誤解2**: 「ウォーターフォールは古い」→ 正解：適切な場面では有効
- **誤解3**: 「ドキュメント不要」→ 正解：必要最小限のドキュメントは重要

## 10. 理解度確認クイズ（4択問題20問）

### 問題1
ウォーターフォールモデルの特徴として最も適切なものはどれか？

- A) 各フェーズを繰り返しながら開発を進める
- B) リスク分析を各サイクルで実施する
- C) 上流工程から下流工程へ順次進行する
- D) 2-4週間のスプリントで開発する

<details>
<summary>解答</summary>
<strong>正解: C</strong><br>
ウォーターフォールモデルは、要求定義→設計→実装→テスト→運用という順序で、上流から下流へ一方向に進む開発モデルです。<br>
<br>
Aが間違いの理由：繰り返し開発はスパイラルやアジャイルの特徴<br>
Bが間違いの理由：リスク分析の反復はスパイラルモデルの特徴<br>
Dが間違いの理由：スプリント開発はスクラムの特徴
</details>

### 問題2
スパイラルモデルの4つの基本活動に含まれないものはどれか？

- A) 目標設定
- B) リスク分析
- C) ペアプログラミング
- D) 開発と検証

<details>
<summary>解答</summary>
<strong>正解: C</strong><br>
スパイラルモデルの4つの基本活動は、目標設定、リスク分析、開発と検証、計画です。<br>
<br>
Cのペアプログラミングは、エクストリームプログラミング（XP）のプラクティスであり、スパイラルモデルの基本活動ではありません。
</details>

### 問題3
インクリメンタルモデルの最大の利点はどれか？

- A) 詳細なドキュメントが作成できる
- B) 部分的でも早期に価値提供できる
- C) リスク分析が徹底的に行える
- D) 変更が一切発生しない

## 11. 専門用語集

このスライドで使用された専門用語について、アルファベット順・50音順で解説します。

### アルファベット

**ASD (Adaptive Software Development)**
- **読み方**: エーエスディー、適応型ソフトウェア開発
- **意味**: 複雑適応系理論に基づき、変化を前提として推測・協調・学習のサイクルで進めるアジャイル開発手法
- **関連用語**: アジャイル開発、複雑適応系

**CI (Continuous Integration)**
- **読み方**: シーアイ、継続的インテグレーション
- **意味**: 開発者のコードを頻繁に統合し、自動ビルド・テストを実行する開発プラクティス
- **関連用語**: DevOps、自動化、ビルド

**Crystal**
- **読み方**: クリスタル
- **意味**: プロジェクトの規模と重要度に応じて手法を調整するアジャイル開発手法ファミリー
- **関連用語**: Crystal Clear、Crystal Yellow、Crystal Orange

**DSDM (Dynamic Systems Development Method)**
- **読み方**: ディーエスディーエム、動的システム開発手法
- **意味**: ビジネス価値の早期提供に焦点を当て、時間とリソースを固定して機能を調整するアジャイル手法
- **関連用語**: タイムボックス、MoSCoW分析

**FDD (Feature Driven Development)**
- **読み方**: エフディーディー、フィーチャー駆動開発
- **意味**: 機能（フィーチャー）を中心に、モデリングと反復的な開発を組み合わせたアジャイル手法
- **関連用語**: フィーチャー、ドメインモデル

**PO (Product Owner)**
- **読み方**: ピーオー、プロダクトオーナー
- **意味**: スクラムにおいて、プロダクトバックログを管理し、ビジネス価値を最大化する役割
- **関連用語**: スクラム、プロダクトバックログ

**SDLC (Software Development Life Cycle)**
- **読み方**: エスディーエルシー、ソフトウェア開発ライフサイクル
- **意味**: ソフトウェアの構想から廃棄までの全過程を体系化したもの
- **関連用語**: 開発プロセス、ライフサイクル

**SM (Scrum Master)**
- **読み方**: エスエム、スクラムマスター
- **意味**: スクラムプロセスの促進と障害の除去を担当し、チームの自己組織化を支援する役割
- **関連用語**: スクラム、ファシリテーター

**TDD (Test Driven Development)**
- **読み方**: ティーディーディー、テスト駆動開発
- **意味**: テストを先に書いてから実装を行う開発手法。Red-Green-Refactorのサイクルで進める
- **関連用語**: 単体テスト、リファクタリング、XP

**WIP (Work In Progress)**
- **読み方**: ウィップ、仕掛かり作業
- **意味**: 現在進行中の作業。カンバンではWIP制限により同時進行作業数を制限する
- **関連用語**: カンバン、フロー、ボトルネック

**XP (Extreme Programming)**
- **読み方**: エックスピー、エクストリームプログラミング
- **意味**: プログラミングに焦点を当て、ペアプログラミングやTDDなどのプラクティスを重視するアジャイル手法
- **関連用語**: ペアプログラミング、TDD、継続的インテグレーション

### あ行

**アジャイル開発（Agile Development）**
- **読み方**: あじゃいるかいはつ
- **意味**: 反復的で柔軟な開発手法の総称。変化への適応と顧客との協調を重視する
- **関連用語**: スクラム、XP、カンバン、アジャイル宣言

**アジャイル宣言（Agile Manifesto）**
- **読み方**: あじゃいるせんげん
- **意味**: 2001年に発表された、アジャイル開発の価値観と原則を定めた文書
- **関連用語**: アジャイル開発、4つの価値、12の原則

**インクリメンタルモデル（Incremental Model）**
- **読み方**: いんくりめんたるもでる
- **意味**: システムを複数の増分に分割し、各増分を順次開発・リリースする開発モデル
- **関連用語**: 増分、段階的リリース、反復開発

**インクリメント（Increment）**
- **読み方**: いんくりめんと
- **意味**: スクラムにおいて、スプリント終了時に完成している成果物。または増分開発における一つの開発単位
- **関連用語**: スプリント、完成の定義、増分

**ウォーターフォールモデル（Waterfall Model）**
- **読み方**: うぉーたーふぉーるもでる
- **意味**: 上流工程から下流工程へ順次進行する、最も伝統的な開発モデル
- **関連用語**: 要求定義、設計、実装、テスト、V字モデル

### か行

**カンバン（Kanban）**
- **読み方**: かんばん
- **意味**: トヨタ生産方式から派生した、視覚的な作業管理手法。作業の可視化とWIP制限が特徴
- **関連用語**: カンバンボード、WIP制限、プル型システム

**カンバンボード（Kanban Board）**
- **読み方**: かんばんぼーど
- **意味**: 作業の状態を視覚的に表示するボード。通常「To Do」「In Progress」「Done」などの列で構成
- **関連用語**: カンバン、視覚化、フロー管理

**クロスファンクショナルチーム（Cross-functional Team）**
- **読み方**: くろすふぁんくしょなるちーむ
- **意味**: 異なる専門分野のメンバーで構成され、製品開発に必要なすべてのスキルを持つチーム
- **関連用語**: 自己組織化チーム、スクラムチーム

**継続的インテグレーション（Continuous Integration）**
- **読み方**: けいぞくてきいんてぐれーしょん
- **意味**: 開発者のコードを頻繁に統合し、自動ビルド・テストを実行する開発プラクティス
- **関連用語**: CI、自動化、DevOps

### さ行

**自己組織化チーム（Self-organizing Team）**
- **読み方**: じこそしきかちーむ
- **意味**: 外部からの指示ではなく、チーム内で作業の進め方を決定し、問題を解決できるチーム
- **関連用語**: アジャイル、エンパワーメント、自律性

**スクラム（Scrum）**
- **読み方**: すくらむ
- **意味**: 最も広く採用されているアジャイル開発手法。3つの役割、5つのイベント、3つの成果物で構成
- **関連用語**: スプリント、プロダクトオーナー、スクラムマスター

**スパイラルモデル（Spiral Model）**
- **読み方**: すぱいらるもでる
- **意味**: リスク駆動型の開発モデル。螺旋状に開発を繰り返しながら段階的にシステムを完成させる
- **関連用語**: リスク分析、プロトタイプ、反復開発

**スプリント（Sprint）**
- **読み方**: すぷりんと
- **意味**: スクラムにおける固定期間（通常1-4週間）の開発サイクル
- **関連用語**: スクラム、タイムボックス、スプリントゴール

**スプリントバックログ（Sprint Backlog）**
- **読み方**: すぷりんとばっくろぐ
- **意味**: スプリント期間中に完了すべき作業項目のリスト
- **関連用語**: プロダクトバックログ、スプリントプランニング

**スプリントプランニング（Sprint Planning）**
- **読み方**: すぷりんとぷらんにんぐ
- **意味**: スプリントの開始時に行う計画会議。何を作るか、どのように作るかを決定
- **関連用語**: スプリント、プロダクトバックログ、スプリントゴール

**スプリントレトロスペクティブ（Sprint Retrospective）**
- **読み方**: すぷりんとれとろすぺくてぃぶ
- **意味**: スプリント終了時に行う振り返り会議。改善点を特定し、次のスプリントに活かす
- **関連用語**: 振り返り、継続的改善、検査と適応

**スプリントレビュー（Sprint Review）**
- **読み方**: すぷりんとれびゅー
- **意味**: スプリント終了時に成果物をデモし、ステークホルダーからフィードバックを得る会議
- **関連用語**: デモ、インクリメント、ステークホルダー

### た行

**タイムボックス（Time-box）**
- **読み方**: たいむぼっくす
- **意味**: 固定された時間枠。スクラムではすべてのイベントがタイムボックス化されている
- **関連用語**: スプリント、固定期間、時間管理

**デイリースクラム（Daily Scrum）**
- **読み方**: でいりーすくらむ
- **意味**: 毎日同じ時間・場所で行う15分間の同期会議。進捗確認と障害の共有を行う
- **関連用語**: スタンドアップミーティング、日次会議

**テスト駆動開発（Test Driven Development）**
- **読み方**: てすとくどうかいはつ
- **意味**: テストを先に書いてから実装を行う開発手法。Red-Green-Refactorのサイクルで進める
- **関連用語**: TDD、単体テスト、XP

### な行

**ナビゲーター（Navigator）**
- **読み方**: なびげーたー
- **意味**: ペアプログラミングにおいて、全体的な方向性を考え、ドライバーに指示を出す役割
- **関連用語**: ペアプログラミング、ドライバー、XP

### は行

**バックログ（Backlog）**
- **読み方**: ばっくろぐ
- **意味**: 実施すべき作業項目のリスト。優先順位付けされ、継続的に更新される
- **関連用語**: プロダクトバックログ、スプリントバックログ

**反復開発（Iterative Development）**
- **読み方**: はんぷくかいはつ
- **意味**: 短い期間で開発サイクルを繰り返し、段階的にシステムを構築する開発手法
- **関連用語**: イテレーション、アジャイル、インクリメンタル

**フィーチャー（Feature）**
- **読み方**: ふぃーちゃー
- **意味**: FDDにおける開発の単位。ユーザーに価値を提供する小さな機能
- **関連用語**: FDD、機能、ユーザー価値

**プロダクトバックログ（Product Backlog）**
- **読み方**: ぷろだくとばっくろぐ
- **意味**: 製品に必要なすべての機能・要求のリスト。プロダクトオーナーが管理
- **関連用語**: バックログ、優先順位、プロダクトオーナー

**プロトタイプ（Prototype）**
- **読み方**: ぷろとたいぷ
- **意味**: システムの一部または全体の試作品。要求の確認やリスクの検証に使用
- **関連用語**: スパイラルモデル、検証、モックアップ

**ペアプログラミング（Pair Programming）**
- **読み方**: ぺあぷろぐらみんぐ
- **意味**: 2人1組でプログラミングを行うXPのプラクティス。ドライバーとナビゲーターの役割を交代
- **関連用語**: XP、ドライバー、ナビゲーター

**ベロシティ（Velocity）**
- **読み方**: べろしてぃ
- **意味**: スクラムチームが1スプリントで完了できる作業量の指標
- **関連用語**: スプリント、見積もり、計画

### ま行

**モブプログラミング（Mob Programming）**
- **読み方**: もぶぷろぐらみんぐ
- **意味**: 3人以上のチーム全員で1つのコンピュータを使ってプログラミングする手法
- **関連用語**: ペアプログラミング、協調作業

### や行

**ユーザーストーリー（User Story）**
- **読み方**: ゆーざーすとーりー
- **意味**: ユーザーの視点から書かれた要求の記述。「誰が」「何を」「なぜ」の形式で表現
- **関連用語**: 要求定義、アジャイル、プロダクトバックログ

### ら行

**リーンソフトウェア開発（Lean Software Development）**
- **読み方**: りーんそふとうぇあかいはつ
- **意味**: トヨタ生産方式の原則をソフトウェア開発に適用した手法。無駄の排除を重視
- **関連用語**: 無駄の排除、価値の流れ、継続的改善

**リスク駆動（Risk-driven）**
- **読み方**: りすくくどう
- **意味**: リスクの高い要素から優先的に対処する開発アプローチ
- **関連用語**: スパイラルモデル、リスク分析、リスク管理

**リファクタリング（Refactoring）**
- **読み方**: りふぁくたりんぐ
- **意味**: 外部から見た動作を変えずに、コードの内部構造を改善すること
- **関連用語**: TDD、コード品質、技術的負債

**レトロスペクティブ（Retrospective）**
- **読み方**: れとろすぺくてぃぶ
- **意味**: 振り返り。過去の活動を評価し、改善点を見つけ出すプロセス
- **関連用語**: スプリントレトロスペクティブ、継続的改善、PDCA

### わ行

**ワークインプログレス（Work In Progress）**
- **読み方**: わーくいんぷろぐれす
- **意味**: 現在進行中の作業。WIPと略される。カンバンではこれを制限することでフローを改善
- **関連用語**: WIP、カンバン、フロー効率
