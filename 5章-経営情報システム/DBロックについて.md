# DBロックについて

## 概要
データベースにおけるロック機構は、複数のトランザクションが同時にデータベースにアクセスする際の一貫性と整合性を保証する重要な仕組みです。ロックは、同時実行制御（Concurrency Control）の中核を成す技術であり、トランザクションの分離性（Isolation）を実現します。

## 1. 基本概念・仕組み

### ロックとは
- **定義**: トランザクションがデータベース内のリソース（行、テーブル、ページなど）に対して一時的に排他的または共有的なアクセス権を取得する仕組み
- **動作原理**: トランザクションがリソースを使用する前にロックを取得し、使用後に解放することで、他のトランザクションとの競合を防ぐ
- **特徴**: 悲観的並行性制御の代表的な手法で、デッドロックの可能性がある一方、確実な整合性を保証

### ACID特性との関係
- **従来技術との違い**: ファイルシステムでの単純な排他制御と異なり、きめ細かい粒度でのロック制御が可能
- **改善点**: トランザクションの分離レベルに応じた柔軟なロック戦略を実現
- **限界**: デッドロックの完全な回避は困難で、パフォーマンスとの両立が課題

## 2. 種類・分類

### ロックモードによる分類
データベースロックは、アクセスの排他性によって主に2つのモードに分類されます。

### 共有ロック（Shared Lock, S-Lock）
**特徴:**
- 読み取り専用のロック
- 複数のトランザクションが同時に同じリソースに対して共有ロックを取得可能
- 書き込み操作をブロック

**算出方法:**
```sql
-- 共有ロックの取得例（SQL Server）
BEGIN TRANSACTION
SELECT * FROM テーブル名 WITH (HOLDLOCK)
WHERE 条件
```

**📊 具体的な計算例**
**例: オンラインショップの在庫確認**
- 前提条件1: 商品ID=100の在庫数を確認
- 前提条件2: 複数ユーザーが同時に確認可能

**ステップ1: トランザクションAが共有ロック取得**
```sql
-- トランザクションA
BEGIN TRANSACTION
SELECT 在庫数 FROM 商品 WITH (HOLDLOCK)
WHERE 商品ID = 100
-- 結果: 在庫数 = 50
```

**ステップ2: トランザクションBも共有ロック取得**
```sql
-- トランザクションB（同時実行可能）
BEGIN TRANSACTION
SELECT 在庫数 FROM 商品 WITH (HOLDLOCK)
WHERE 商品ID = 100
-- 結果: 在庫数 = 50
```

**結果: 両方のトランザクションが同時に読み取り可能**

💡 **実際の現場では**: 共有ロックは報告書作成やデータ分析など、読み取り専用の処理で広く使用されます。

### 占有ロック（Exclusive Lock, X-Lock）
**特徴:**
- 読み書き両方を排他的に制御
- 一つのトランザクションのみがリソースに対して占有ロックを取得可能
- 他のすべてのロック（共有・占有）をブロック

**算出方法:**
```sql
-- 占有ロックの取得例（SQL Server）
BEGIN TRANSACTION
UPDATE テーブル名 WITH (XLOCK)
SET カラム = 値
WHERE 条件
```

**📊 具体的な計算例**
**例: 在庫数の更新処理**
- 前提条件1: 商品ID=100の在庫を10個減らす
- 前提条件2: 同時に複数の注文処理が発生

**ステップ1: トランザクションCが占有ロック取得**
```sql
-- トランザクションC
BEGIN TRANSACTION
UPDATE 商品 WITH (XLOCK)
SET 在庫数 = 在庫数 - 10
WHERE 商品ID = 100
-- 占有ロックを取得、他のトランザクションはブロックされる
```

**ステップ2: トランザクションDがアクセス試行**
```sql
-- トランザクションD（ブロックされる）
BEGIN TRANSACTION
SELECT 在庫数 FROM 商品
WHERE 商品ID = 100
-- トランザクションCがコミットするまで待機
```

**結果: 占有ロックが解放されるまで他のトランザクションは待機**

💡 **実際の現場では**: 占有ロックは在庫更新、口座振替、マスタデータ更新など、データの整合性が重要な処理で使用されます。

## 3. 詳細仕様・パラメータ

### ロックの粒度（Granularity）
#### 行レベルロック
- **意味**: 単一の行に対してロックを適用
- **設定範囲**: 1行単位
- **影響**: 並行性は高いが、ロック管理のオーバーヘッドが大きい
- **推奨値**: OLTP環境での標準設定

#### ページレベルロック
- **意味**: データベースページ（通常8KB）単位でロック
- **設定範囲**: 複数行を含むページ単位
- **影響**: 行レベルとテーブルレベルの中間的な特性
- **推奨値**: 中規模のバッチ処理に適用

#### テーブルレベルロック
- **意味**: テーブル全体に対してロックを適用
- **設定範囲**: テーブル全体
- **影響**: 並行性は低いが、ロック管理は単純
- **推奨値**: 大規模なバッチ処理やメンテナンス作業に適用

### ロックのエスカレーション
- **意味**: 細かい粒度のロックが多数になった場合、より粗い粒度のロックに自動変換
- **設定範囲**: DBMS依存（SQL Serverでは5000個の行ロックでテーブルロックへ）
- **影響**: メモリ使用量の削減と引き換えに並行性が低下
- **推奨値**: アプリケーションの特性に応じて閾値を調整

## 4. 実装例・適用事例

### 基本実装
```sql
-- PostgreSQLでの明示的ロック取得
BEGIN;
-- 共有ロック
SELECT * FROM orders WHERE order_id = 1000 FOR SHARE;
-- 占有ロック
SELECT * FROM orders WHERE order_id = 1000 FOR UPDATE;
COMMIT;
```

### 応用実装
```sql
-- デッドロック回避のための順序付きロック取得
BEGIN;
-- 常に同じ順序でロックを取得
SELECT * FROM accounts WHERE account_id = 100 FOR UPDATE;
SELECT * FROM accounts WHERE account_id = 200 FOR UPDATE;
-- 送金処理
UPDATE accounts SET balance = balance - 1000 WHERE account_id = 100;
UPDATE accounts SET balance = balance + 1000 WHERE account_id = 200;
COMMIT;
```

### 実際の適用事例
#### 事例1: 大手ECサイトの在庫管理システム
- **課題**: フラッシュセール時の同時注文による在庫の不整合
- **適用方法**: 楽観的ロックと悲観的ロックのハイブリッド実装
- **結果**: 在庫の不整合を0件に削減
- **効果**: 顧客満足度の向上とクレーム削減

#### 事例2: 銀行の口座振替システム
- **課題**: 高頻度の振替処理でのデッドロック発生
- **適用方法**: 口座番号順でのロック取得ルールを実装
- **結果**: デッドロック発生率を99%削減
- **効果**: システムの安定性向上と処理時間の短縮

## 5. メリット・デメリット

### メリット
**1. データの整合性保証**
- **理由**: トランザクション間の干渉を防ぐ
- **効果**: ACID特性の実現
- **具体例**: 銀行の残高更新で二重引き落としを防止

**2. 実装の容易性**
- **理由**: DBMSが自動的にロック管理を実行
- **効果**: アプリケーション開発の簡素化
- **具体例**: SQL文にFOR UPDATE句を追加するだけで実装可能

### デメリット
**1. デッドロックの可能性**
- **理由**: 複数トランザクションが相互にロック待機
- **影響**: システムの停止やタイムアウト
- **対策**: ロック取得順序の統一、タイムアウト設定

**2. パフォーマンスの低下**
- **理由**: ロック待機によるスループット低下
- **影響**: レスポンスタイムの増加
- **対策**: 適切な粒度の選択、インデックスの最適化

## 6. 選択・導入の指針

### ロック戦略の選択基準
| 観点 | 共有ロック | 占有ロック | 楽観的ロック |
|------|-----------|-----------|--------------|
| 整合性 | ○ | ◎ | △ |
| 並行性 | ○ | △ | ◎ |
| 実装難易度 | ◎ | ◎ | ○ |
| 適用場面 | 読取中心 | 更新中心 | 競合少 |

### 適用判断フローチャート
1. **更新頻度は高いか？** 
   - Yes → 占有ロックまたは楽観的ロック検討
   - No → 次の判断へ

2. **競合の可能性は高いか？**
   - Yes → 悲観的ロック（共有/占有）を選択
   - No → 楽観的ロックを選択

## 7. 最新動向・今後の展望
- **現在の課題**: 分散データベースでのグローバルロックの実現
- **研究動向**: MVCCの高度化、ロックフリーアルゴリズムの実用化
- **将来予測**: AIによる動的なロック戦略の最適化
- **関連技術**: 楽観的並行性制御、MVCC、2フェーズロッキング

## 8. 理解度確認クイズ（4択問題20問）

### 問題1
共有ロック（S-Lock）の特徴として正しいものはどれか？

- A) 一つのトランザクションのみが取得可能
- B) 複数のトランザクションが同時に取得可能
- C) 書き込み操作が可能
- D) 他の共有ロックをブロックする

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
共有ロックは読み取り専用のロックで、複数のトランザクションが同じリソースに対して同時に共有ロックを取得できます。<br>
<br>
Aが間違いの理由：これは占有ロックの特徴です<br>
Cが間違いの理由：共有ロックは読み取り専用で書き込みはできません<br>
Dが間違いの理由：共有ロック同士は互いにブロックしません<br>
<br>
【補足】実務では、レポート作成や集計処理など、データを読むだけの処理で共有ロックが使用されます。
</details>

### 問題2
占有ロック（X-Lock）について誤っているものはどれか？

- A) 読み書き両方の操作が可能
- B) 他のすべてのロックをブロックする
- C) 複数のトランザクションが同時に取得できる
- D) データの更新時に使用される

<details>
<summary>解答</summary>
<strong>正解: C</strong><br>
占有ロックは排他的なロックであり、一つのトランザクションのみが取得可能です。複数のトランザクションが同時に取得することはできません。<br>
<br>
Aが正しい理由：占有ロックは読み書き両方の操作が可能です<br>
Bが正しい理由：占有ロックは他のすべてのロック（共有・占有）をブロックします<br>
Dが正しい理由：データの更新時には占有ロックが使用されます<br>
<br>
【補足】占有ロックは在庫更新や口座振替など、データの整合性が重要な処理で使用されます。
</details>

### 問題3
ロックの粒度について、並行性が最も高いものはどれか？

- A) データベースレベルロック
- B) テーブルレベルロック
- C) ページレベルロック
- D) 行レベルロック

<details>
<summary>解答</summary>
<strong>正解: D</strong><br>
行レベルロックは最も細かい粒度のロックで、他のトランザクションへの影響が最小限となるため、並行性が最も高くなります。<br>
<br>
Aが間違いの理由：データベース全体をロックするため並行性は最も低い<br>
Bが間違いの理由：テーブル全体をロックするため並行性は低い<br>
Cが間違いの理由：ページ単位のロックは行レベルより粗い粒度<br>
<br>
【補足】ただし、行レベルロックはロック管理のオーバーヘッドが大きいという欠点もあります。
</details>

### 問題4
次のSQL文で取得されるロックの種類は？
```sql
SELECT * FROM products WHERE product_id = 100 FOR UPDATE;
```

- A) 共有ロック
- B) 占有ロック
- C) 意図的ロック
- D) 更新ロック

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
FOR UPDATE句は占有ロック（排他ロック）を取得します。これにより、他のトランザクションは該当行に対する読み書きがブロックされます。<br>
<br>
Aが間違いの理由：FOR SHAREやLOCK IN SHARE MODEが共有ロックを取得<br>
Cが間違いの理由：意図的ロックは上位レベルのロックを示すメタロック<br>
Dが間違いの理由：更新ロックは一部のDBMSでの特殊なロックモード<br>
<br>
【補足】FOR UPDATE句は、後続の更新処理のために事前にロックを取得する際に使用されます。
</details>

### 問題5
デッドロックが発生する条件として誤っているものはどれか？

- A) 相互排他条件
- B) 保持と待機条件
- C) 非横取り条件
- D) 時間制限条件

<details>
<summary>解答</summary>
<strong>正解: D</strong><br>
デッドロックの発生条件（Coffman条件）は、相互排他、保持と待機、非横取り、循環待機の4つです。時間制限条件は含まれません。<br>
<br>
Aが正しい理由：リソースが排他的に使用される条件<br>
Bが正しい理由：リソースを保持しながら他のリソースを待つ条件<br>
Cが正しい理由：リソースを強制的に解放できない条件<br>
<br>
【補足】4つ目の条件は「循環待機条件」で、これら4つすべてが満たされるとデッドロックが発生します。
</details>

### 問題6
ロックエスカレーションが発生する主な理由は？

- A) CPUの負荷が高いため
- B) ディスクI/Oが遅いため
- C) 細かい粒度のロックが多数になったため
- D) ネットワークが遅延したため

<details>
<summary>解答</summary>
<strong>正解: C</strong><br>
ロックエスカレーションは、行レベルなどの細かい粒度のロックが多数（SQL Serverでは約5000個）になった場合に、メモリ使用量を削減するために自動的により粗い粒度（テーブルレベル）のロックに変換される現象です。<br>
<br>
Aが間違いの理由：CPU負荷は直接的な原因ではない<br>
Bが間違いの理由：ディスクI/Oはロックエスカレーションと無関係<br>
Dが間違いの理由：ネットワーク遅延は関係ない<br>
<br>
【補足】ロックエスカレーションは並行性を犠牲にしてメモリ効率を改善する仕組みです。
</details>

### 問題7
2フェーズロッキングプロトコルの「成長フェーズ」で行うことは？

- A) ロックの取得のみ
- B) ロックの解放のみ
- C) ロックの取得と解放の両方
- D) ロックの変換のみ

<details>
<summary>解答</summary>
<strong>正解: A</strong><br>
2フェーズロッキングプロトコルでは、成長フェーズ（Growing Phase）でロックの取得のみを行い、縮小フェーズ（Shrinking Phase）でロックの解放のみを行います。<br>
<br>
Bが間違いの理由：ロックの解放は縮小フェーズで行う<br>
Cが間違いの理由：各フェーズで取得と解放を混在させない<br>
Dが間違いの理由：ロック変換は特定のフェーズに限定されない<br>
<br>
【補足】このプロトコルにより、トランザクションの直列可能性が保証されます。
</details>

### 問題8
楽観的ロックと悲観的ロックの違いとして正しいものは？

- A) 楽観的ロックはロックを使用しない
- B) 悲観的ロックはデッドロックが発生しない
- C) 楽観的ロックは更新時のみ競合をチェックする
- D) 悲観的ロックは読み取り時にロックしない

<details>
<summary>解答</summary>
<strong>正解: C</strong><br>
楽観的ロックは、データ読み取り時にはロックせず、更新時にバージョン番号やタイムスタンプで競合をチェックします。<br>
<br>
Aが間違いの理由：楽観的ロックもバージョン管理などの仕組みを使用<br>
Bが間違いの理由：悲観的ロックでもデッドロックは発生する可能性がある<br>
Dが間違いの理由：悲観的ロックは読み取り時からロックする<br>
<br>
【補足】楽観的ロックは競合が少ない環境で高い性能を発揮します。
</details>

### 問題9
MVCCにおいて、各トランザクションが参照するデータのバージョンを決定する基準は？

- A) トランザクションID
- B) トランザクション開始時刻
- C) ロックの取得順序
- D) データの更新頻度

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
MVCC（Multi-Version Concurrency Control）では、トランザクション開始時刻（スナップショット時刻）を基準に、その時点で確定していたデータのバージョンを参照します。<br>
<br>
Aが間違いの理由：トランザクションIDは識別子であり、バージョン決定の直接的な基準ではない<br>
Cが間違いの理由：MVCCはロックを最小限にする仕組み<br>
Dが間違いの理由：更新頻度は関係ない<br>
<br>
【補足】PostgreSQLやOracleなどの主要なDBMSでMVCCが実装されています。
</details>

### 問題10
インテンションロック（意図的ロック）の目的は？

- A) デッドロックを防ぐため
- B) ロック競合を効率的に検出するため
- C) トランザクションを高速化するため
- D) メモリ使用量を削減するため

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
インテンションロックは、階層的なロック構造において、上位レベル（テーブル）に意図を示すロックを設定することで、下位レベル（行）とのロック競合を効率的に検出できるようにする仕組みです。<br>
<br>
Aが間違いの理由：デッドロック防止が主目的ではない<br>
Cが間違いの理由：直接的な高速化が目的ではない<br>
Dが間違いの理由：メモリ削減が主目的ではない<br>
<br>
【補足】IS（意図的共有）、IX（意図的排他）などの種類があります。
</details>

### 問題11
次のシナリオで適切なロック戦略は？
「ECサイトで商品の在庫数を確認し、在庫があれば注文処理を行う」

- A) 在庫確認時に共有ロック、注文時に占有ロック
- B) 最初から占有ロックで在庫確認と注文処理
- C) ロックを使わず楽観的並行性制御
- D) 在庫確認時に占有ロック、注文時にロック解放

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
在庫確認から注文処理まで一貫して占有ロックを保持することで、他のトランザクションによる在庫の変更を防ぎ、在庫の整合性を保証できます。<br>
<br>
Aが間違いの理由：共有ロックから占有ロックへの昇格時にデッドロックのリスク<br>
Cが間違いの理由：高頻度の注文では競合によるリトライが多発する可能性<br>
Dが間違いの理由：ロック解放後に他のトランザクションが在庫を変更する可能性<br>
<br>
【補足】SELECT FOR UPDATEを使用して、読み取り時点で占有ロックを取得するのが一般的です。
</details>

### 問題12
デッドロックの回避策として最も効果的なものは？

- A) トランザクションの実行時間を長くする
- B) すべてのテーブルをロックしてから処理を開始
- C) リソースへのアクセス順序を統一する
- D) ロックタイムアウトを無効にする

<details>
<summary>解答</summary>
<strong>正解: C</strong><br>
すべてのトランザクションで同じ順序（例：テーブルA→テーブルB）でリソースにアクセスすることで、循環待機を防ぎ、デッドロックを回避できます。<br>
<br>
Aが間違いの理由：実行時間を長くするとデッドロックの可能性が増加<br>
Bが間違いの理由：並行性が著しく低下し、実用的でない<br>
Dが間違いの理由：タイムアウト無効化はデッドロック時に永続的な待機となる<br>
<br>
【補足】銀行システムでは口座番号順にロックを取得するなどの実装が一般的です。
</details>

### 問題13
ロック粒度の選択において、OLTPシステムで推奨される設定は？

- A) データベースレベルロック
- B) テーブルレベルロック
- C) ページレベルロック
- D) 行レベルロック

<details>
<summary>解答</summary>
<strong>正解: D</strong><br>
OLTP（Online Transaction Processing）システムは、小規模で高頻度なトランザクションが特徴のため、行レベルロックによる高い並行性が求められます。<br>
<br>
Aが間違いの理由：並行性が極端に低く、OLTPには不適切<br>
Bが間違いの理由：テーブル全体のロックは並行性を大きく損なう<br>
Cが間違いの理由：ページレベルでは不要な行までロックされる可能性<br>
<br>
【補足】一方、バッチ処理やDWHではテーブルレベルロックが適している場合があります。
</details>

### 問題14
分離レベル「READ COMMITTED」で防げる現象は？

- A) ダーティリード
- B) ファントムリード
- C) 反復不能読み取り
- D) ロスト・アップデート

<details>
<summary>解答</summary>
<strong>正解: A</strong><br>
READ COMMITTEDは、コミットされていないデータの読み取り（ダーティリード）を防ぎますが、ファントムリードや反復不能読み取りは防げません。<br>
<br>
Bが間違いの理由：ファントムリードを防ぐにはSERIALIZABLEが必要<br>
Cが間違いの理由：反復不能読み取りを防ぐにはREPEATABLE READが必要<br>
Dが間違いの理由：ロスト・アップデートの防止には適切なロック戦略が必要<br>
<br>
【補足】多くのDBMSでREAD COMMITTEDがデフォルトの分離レベルです。
</details>

### 問題15
次のコードでデッドロックが発生する可能性がある理由は？
```sql
-- トランザクション1
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- トランザクション2
UPDATE accounts SET balance = balance - 50 WHERE id = 2;
UPDATE accounts SET balance = balance + 50 WHERE id = 1;
```

- A) 更新金額が異なるため
- B) アクセス順序が逆のため
- C) トランザクションが同時実行されるため
- D) UPDATEを使用しているため

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
トランザクション1はid=1→id=2の順、トランザクション2はid=2→id=1の順でアクセスするため、相互にロック待機してデッドロックが発生する可能性があります。<br>
<br>
Aが間違いの理由：金額の違いはデッドロックと無関係<br>
Cが間違いの理由：同時実行は必要条件だが、直接的な原因ではない<br>
Dが間違いの理由：UPDATE自体が問題ではなく、順序が問題<br>
<br>
【補足】両方のトランザクションでid順（昇順）にアクセスすれば回避できます。
</details>

### 問題16
ギャップロックが使用される主な目的は？

- A) テーブル全体の高速ロック
- B) ファントムリードの防止
- C) デッドロックの解消
- D) メモリ使用量の削減

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
ギャップロックは、存在しない範囲（ギャップ）に対してロックをかけることで、他のトランザクションがその範囲に新しい行を挿入することを防ぎ、ファントムリードを防止します。<br>
<br>
Aが間違いの理由：ギャップロックは範囲ロックであり、テーブル全体ではない<br>
Cが間違いの理由：デッドロック解消が目的ではない<br>
Dが間違いの理由：メモリ削減が主目的ではない<br>
<br>
【補足】InnoDBストレージエンジンでREPEATABLE READ以上の分離レベルで使用されます。
</details>

### 問題17
オンラインバックアップ中のロック戦略として適切なものは？

- A) データベース全体を占有ロック
- B) バックアップ対象を共有ロック
- C) ロックを使用しない
- D) 一時的にすべてのトランザクションを停止

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
オンラインバックアップでは、データの一貫性を保ちながら通常業務を継続するため、バックアップ対象に共有ロックをかけて読み取り、更新はブロックしない方式が適切です。<br>
<br>
Aが間違いの理由：占有ロックでは業務が完全に停止してしまう<br>
Cが間違いの理由：ロックなしでは一貫性のあるバックアップが取得できない<br>
Dが間違いの理由：オンラインバックアップの意味がなくなる<br>
<br>
【補足】最新のDBMSではMVCCを利用したより影響の少ないバックアップも可能です。
</details>

### 問題18
ロックの保持期間について、一般的な推奨事項は？

- A) できるだけ長く保持する
- B) 必要最小限の期間に留める
- C) トランザクション終了後も保持する
- D) 固定時間（例：5秒）保持する

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
ロックは必要最小限の期間に留めるべきです。長時間のロック保持は他のトランザクションをブロックし、システム全体のスループットを低下させます。<br>
<br>
Aが間違いの理由：長時間のロックは並行性を著しく低下させる<br>
Cが間違いの理由：トランザクション終了時にロックは解放されるべき<br>
Dが間違いの理由：処理内容に関係なく固定時間は非効率<br>
<br>
【補足】具体的には、必要なデータを取得したら速やかに処理し、COMMITすることが重要です。
</details>

### 問題19
分散データベースにおけるグローバルデッドロックの検出が困難な理由は？

- A) ネットワーク遅延があるため
- B) 各ノードが独立してロック管理するため
- C) データ量が多いため
- D) トランザクションが複雑なため

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
分散データベースでは各ノードが独立してロック管理を行うため、ノード間にまたがる循環待機（グローバルデッドロック）の検出には、全ノードの情報を収集・分析する必要があり困難です。<br>
<br>
Aが間違いの理由：遅延は性能に影響するが、検出困難の本質的理由ではない<br>
Cが間違いの理由：データ量は直接的な原因ではない<br>
Dが間違いの理由：複雑さは要因の一つだが、主要因は分散管理<br>
<br>
【補足】タイムアウトや分散デッドロック検出アルゴリズムで対処します。
</details>

### 問題20
NoSQLデータベースでロック機構が簡略化されている理由は？

- A) 性能が低いため
- B) 結果整合性モデルを採用しているため
- C) データ量が少ないため
- D) 単純なデータ構造のため

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
多くのNoSQLデータベースは、強い一貫性よりもスケーラビリティを重視し、結果整合性（Eventual Consistency）モデルを採用しているため、厳密なロック機構が簡略化されています。<br>
<br>
Aが間違いの理由：NoSQLは高性能を目指して設計されている<br>
Cが間違いの理由：NoSQLはビッグデータ処理にも使用される<br>
Dが間違いの理由：データ構造の複雑さとロック機構は直接関係ない<br>
<br>
【補足】ただし、一部のNoSQLでもACID特性をサポートするものが増えています。
</details>

## 9. 専門用語集

このドキュメントで使用された技術用語について、アルファベット順・50音順で解説します。

### アルファベット

**ACID**
- **読み方**: エーシーアイディー
- **意味**: データベーストランザクションの4つの重要な特性（Atomicity：原子性、Consistency：一貫性、Isolation：独立性、Durability：永続性）を表す頭字語
- **関連用語**: トランザクション、分離レベル、一貫性

**Deadlock**
- **読み方**: デッドロック
- **意味**: 複数のトランザクションが互いに相手の持つリソースを待ち合い、処理が進まなくなる状態
- **関連用語**: ロック、循環待機、タイムアウト

**MVCC (Multi-Version Concurrency Control)**
- **読み方**: エムブイシーシー
- **意味**: データの複数バージョンを保持することで、読み取りと書き込みの競合を減らす並行性制御手法
- **関連用語**: スナップショット、楽観的ロック、PostgreSQL

**OLTP (Online Transaction Processing)**
- **読み方**: オーエルティーピー
- **意味**: リアルタイムでトランザクションを処理するシステム。小規模で高頻度な処理が特徴
- **関連用語**: トランザクション処理、リアルタイム処理、OLAP

**S-Lock (Shared Lock)**
- **読み方**: エスロック
- **意味**: 共有ロックの略称。複数のトランザクションが同時に取得可能な読み取り専用ロック
- **関連用語**: 共有ロック、読み取りロック、X-Lock

**X-Lock (Exclusive Lock)**
- **読み方**: エックスロック
- **意味**: 占有ロック（排他ロック）の略称。一つのトランザクションのみが取得可能な読み書き両用ロック
- **関連用語**: 占有ロック、排他ロック、S-Lock

### あ行

**インテンションロック（意図的ロック）**
- **読み方**: いんてんしょんろっく
- **意味**: 階層的なロック構造で、上位レベルに下位レベルでのロック意図を示すために設定されるロック
- **関連用語**: IS（意図的共有）、IX（意図的排他）、階層的ロック

**エスカレーション**
- **読み方**: えすかれーしょん
- **意味**: 細かい粒度のロックが多数になった場合に、自動的により粗い粒度のロックに変換される現象
- **関連用語**: ロック粒度、メモリ管理、パフォーマンス

### か行

**楽観的ロック**
- **読み方**: がっかんてきろっく
- **意味**: データ読み取り時にはロックせず、更新時に競合をチェックする並行性制御手法
- **関連用語**: バージョン管理、タイムスタンプ、悲観的ロック

**ギャップロック**
- **読み方**: ぎゃっぷろっく
- **意味**: インデックスレコード間の「ギャップ」に対するロックで、新規挿入を防ぐ
- **関連用語**: ファントムリード、範囲ロック、InnoDB

**共有ロック**
- **読み方**: きょうゆうろっく
- **意味**: 複数のトランザクションが同時に取得可能な読み取り専用のロック
- **関連用語**: S-Lock、読み取りロック、占有ロック

**行レベルロック**
- **読み方**: ぎょうれべるろっく
- **意味**: データベースの個々の行に対して設定される最も細かい粒度のロック
- **関連用語**: ロック粒度、テーブルロック、ページロック

### さ行

**循環待機**
- **読み方**: じゅんかんたいき
- **意味**: 複数のトランザクションが円環状に他のトランザクションのリソースを待つ状態
- **関連用語**: デッドロック、Coffman条件、リソース

**占有ロック**
- **読み方**: せんゆうろっく
- **意味**: 一つのトランザクションのみが取得可能で、他のすべてのアクセスをブロックするロック
- **関連用語**: X-Lock、排他ロック、共有ロック

### た行

**ダーティリード**
- **読み方**: だーてぃりーど
- **意味**: コミットされていないトランザクションのデータを読み取ってしまう現象
- **関連用語**: 分離レベル、READ UNCOMMITTED、一貫性

**デッドロック**
- **読み方**: でっどろっく
- **意味**: 複数のトランザクションが互いに相手の持つリソースを待ち合い、処理が進まなくなる状態
- **関連用語**: 循環待機、タイムアウト、ロック順序

**トランザクション**
- **読み方**: とらんざくしょん
- **意味**: データベースにおける一連の処理をまとめた、不可分な作業単位
- **関連用語**: ACID、コミット、ロールバック

### な行

**二相ロッキング（2フェーズロッキング）**
- **読み方**: にそうろっきんぐ
- **意味**: ロック取得フェーズとロック解放フェーズを分離することで直列可能性を保証するプロトコル
- **関連用語**: 成長フェーズ、縮小フェーズ、直列可能性

### は行

**排他ロック**
- **読み方**: はいたろっく
- **意味**: 占有ロックの別名。他のすべてのアクセスを排除するロック
- **関連用語**: 占有ロック、X-Lock、共有ロック

**悲観的ロック**
- **読み方**: ひかんてきろっく
- **意味**: データアクセス時に事前にロックを取得し、競合を防ぐ並行性制御手法
- **関連用語**: 楽観的ロック、デッドロック、ロック待機

**ファントムリード**
- **読み方**: ふぁんとむりーど
- **意味**: トランザクション内で同じ条件で検索した際に、新たに挿入された行が見える現象
- **関連用語**: 分離レベル、SERIALIZABLE、ギャップロック

**分離レベル**
- **読み方**: ぶんりれべる
- **意味**: トランザクション間の相互影響をどの程度許容するかを定義したレベル
- **関連用語**: READ COMMITTED、REPEATABLE READ、SERIALIZABLE

**ページレベルロック**
- **読み方**: ぺーじれべるろっく
- **意味**: データベースページ（通常8KB）単位で設定されるロック
- **関連用語**: ロック粒度、行ロック、テーブルロック

### ま行

**待ち行列（ロックキュー）**
- **読み方**: まちぎょうれつ
- **意味**: ロックを待機しているトランザクションが並ぶキュー構造
- **関連用語**: ロック待機、タイムアウト、優先度

### ら行

**ロック粒度**
- **読み方**: ろっくりゅうど
- **意味**: ロックを適用する単位の大きさ（行、ページ、テーブルなど）
- **関連用語**: 行ロック、ページロック、テーブルロック

**ロールバック**
- **読み方**: ろーるばっく
- **意味**: トランザクションの変更を取り消し、開始前の状態に戻す操作
- **関連用語**: コミット、トランザクション、ACID
