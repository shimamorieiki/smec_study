# CC（コモンクライテリア）について

## 概要
CC（Common Criteria：コモンクライテリア）は、情報セキュリティ製品の評価・認証に関する国際標準（ISO/IEC 15408）です。IT製品のセキュリティ機能と品質を第三者が客観的に評価するための基準を提供し、政府調達や重要インフラシステムなどで広く採用されています。

## 1. 基本概念・仕組み

### CCの目的と意義
- **定義**: IT製品のセキュリティ機能の信頼性を評価・認証するための国際標準
- **動作原理**: 開発者が作成したセキュリティ仕様（ST：セキュリティターゲット）に基づき、第三者機関が製品を評価
- **特徴**: 
  - 国際相互承認協定（CCRA）により、各国で相互承認される
  - 評価の深さをEAL（評価保証レベル）で段階的に定義
  - プロテクションプロファイル（PP）による要求事項の標準化

### セキュリティ評価の構成要素
- **TOE（Target of Evaluation）**: 評価対象となるIT製品やシステム
- **ST（Security Target）**: 製品のセキュリティ仕様書
- **PP（Protection Profile）**: 製品カテゴリごとのセキュリティ要求事項
- **EAL（Evaluation Assurance Level）**: 評価の厳密さのレベル

## 2. EAL（評価保証レベル）の詳細

### EALレベルの分類
CCでは、評価の深さと厳密さを7段階のEALで定義しています。

### EAL1: 機能テスト
**特徴:**
- 最も基本的な評価レベル
- 独立したテストによる正しい動作の確認
- 脅威が深刻でない環境での使用を想定

**評価内容:**
```
・セキュリティ機能の仕様確認
・基本的な機能テスト
・開発者提供の文書レビュー
```

**📊 具体的な評価例**
**例: Webアプリケーションファイアウォールの評価**
- 前提条件1: 基本的なフィルタリング機能を持つ
- 前提条件2: 一般的な企業環境での使用を想定

**ステップ1: 機能仕様の確認**
```
・URLフィルタリング機能の動作確認
・基本的な攻撃パターンの検知テスト
・管理インターフェースの動作確認
```

**ステップ2: 基本テストの実施**
```
・10種類の攻撃パターンでの動作確認
・正常通信の通過確認
・ログ記録機能の確認
```

**結果: 基本的なセキュリティ機能の動作を保証**

💡 **実際の現場では**: EAL1は低リスク環境での使用に適しており、コストを抑えた評価が可能です。

### EAL2: 構造化テスト
**特徴:**
- 開発者によるテストの確認
- 脆弱性分析の実施
- 構成管理の確認

**評価内容:**
```
・設計文書のレビュー
・開発者テストの独立確認
・既知の脆弱性に対する分析
```

### EAL3: 系統的テストと確認
**特徴:**
- 開発環境のセキュリティ管理確認
- より詳細な設計文書の評価
- 系統的なテスト手法の適用

**評価内容:**
```
・開発環境のセキュリティ評価
・詳細設計文書のレビュー
・侵入テストの実施
```

### EAL4: 系統的設計、テスト、レビュー
**特徴:**
- 商用開発で実現可能な最高レベル
- 完全な開発文書の評価
- 独立した脆弱性分析

**評価内容:**
```
・ソースコードの一部レビュー
・詳細な脆弱性分析
・開発ライフサイクル全体の評価
```

**📊 具体的な評価例**
**例: スマートカード用OSの評価**
- 前提条件1: 金融取引での使用を想定
- 前提条件2: 暗号鍵の安全な管理が必要

**ステップ1: 設計文書の詳細評価**
```
・セキュリティアーキテクチャの分析
・暗号実装の設計レビュー
・アクセス制御機構の評価
```

**ステップ2: ソースコードレビュー**
```
・暗号処理部分のコード検査
・メモリ管理機能の確認
・エラー処理の適切性評価
```

**ステップ3: 侵入テスト**
```
・サイドチャネル攻撃への耐性確認
・フォルト攻撃シミュレーション
・プロトコル実装の脆弱性テスト
```

**結果: 商用利用に十分な保証レベルを達成**

💡 **実際の現場では**: EAL4は多くの政府調達要件を満たし、コストと保証のバランスが良いレベルです。

### EAL5: 準形式的設計とテスト
**特徴:**
- 準形式的な手法による設計
- より厳密なテスト手法
- 高度な脆弱性分析

### EAL6: 準形式的検証済み設計とテスト
**特徴:**
- 準形式的な設計の検証
- 構造化された開発プロセス
- 包括的な分析

### EAL7: 形式的検証済み設計とテスト
**特徴:**
- 形式的手法による完全な検証
- 最高レベルの保証
- 極めて高い脅威環境での使用を想定

## 3. CC評価プロセスの詳細

### 評価プロセスの流れ
1. **準備フェーズ**: 
   - ST（セキュリティターゲット）の作成
   - 評価機関の選定
   - 評価範囲の確定

2. **評価フェーズ**: 
   - 文書評価
   - 製品テスト
   - 脆弱性分析
   - サイト訪問（必要に応じて）

3. **認証フェーズ**: 
   - 評価報告書の作成
   - 認証機関による審査
   - 認証書の発行

### 関連組織と役割
- **開発者**: 製品開発とST作成
- **評価機関**: 第三者評価の実施
- **認証機関**: 評価結果の認証（日本ではIPA）
- **スポンサー**: 評価・認証の依頼者

## 4. プロテクションプロファイル（PP）

### PPの種類と用途
#### スマートカード用PP
- **対象製品**: ICカード、電子パスポート
- **セキュリティ要件**: 暗号機能、アクセス制御、物理的保護
- **典型的なEAL**: EAL4+以上

#### ファイアウォール用PP
- **対象製品**: ネットワークファイアウォール
- **セキュリティ要件**: パケットフィルタリング、ログ機能、管理機能
- **典型的なEAL**: EAL2〜EAL4

#### デジタル複合機用PP
- **対象製品**: オフィス複合機
- **セキュリティ要件**: データ保護、アクセス制御、監査機能
- **典型的なEAL**: EAL2〜EAL3

## 5. 実装例・適用事例

### 政府調達での活用
```
【日本政府の調達基準】
・基本的にEAL3以上を要求
・重要システムではEAL4を要求
・暗号モジュールはFIPS 140-2との組み合わせ
```

### 民間企業での活用事例
#### 事例1: 大手金融機関のATMシステム
- **課題**: カード偽造対策とシステムセキュリティの確保
- **適用方法**: EAL4認証取得製品の採用
- **結果**: セキュリティインシデントの大幅削減
- **効果**: 顧客信頼度の向上と規制要件の充足

#### 事例2: 製造業の制御システム
- **課題**: サイバー攻撃からの重要インフラ保護
- **適用方法**: CC認証済みセキュリティ機器の導入
- **結果**: セキュリティ監査での高評価
- **効果**: 事業継続性の確保

## 6. メリット・デメリット

### メリット
**1. 国際的な相互承認**
- **理由**: CCRA加盟国間での認証結果の相互承認
- **効果**: 複数国での製品展開が容易
- **具体例**: 日本で取得した認証が欧米でも有効

**2. 客観的なセキュリティ評価**
- **理由**: 第三者機関による独立した評価
- **効果**: 製品の信頼性向上
- **具体例**: 政府調達での採用実績

**3. 体系的なセキュリティ要件定義**
- **理由**: PPによる標準化された要件
- **効果**: 開発プロセスの改善
- **具体例**: セキュリティ設計の品質向上

### デメリット
**1. 評価コストと期間**
- **理由**: 詳細な評価プロセス
- **影響**: 数千万円規模のコストと6ヶ月以上の期間
- **対策**: 段階的な認証取得計画

**2. 技術的な複雑性**
- **理由**: 専門知識が必要な文書作成
- **影響**: 専門人材の確保が必要
- **対策**: コンサルタントの活用

**3. 認証の有効期限**
- **理由**: 技術進化への対応
- **影響**: 定期的な再評価が必要
- **対策**: 継続的な保守計画

## 7. CC評価取得の判断基準

### 評価取得判断フローチャート
1. **政府調達要件の確認** 
   - Yes → CC評価が必須
   - No → 次の判断へ

2. **国際展開の予定**
   - Yes → CC評価を推奨
   - No → 次の判断へ

3. **高度なセキュリティ要求**
   - Yes → CC評価を検討
   - No → 他の認証制度を検討

### EALレベル選択の指針
| 利用環境 | 推奨EAL | コスト目安 | 期間目安 |
|---------|---------|-----------|---------|
| 一般オフィス | EAL1-2 | 500-1000万円 | 3-6ヶ月 |
| 企業システム | EAL2-3 | 1000-3000万円 | 6-9ヶ月 |
| 金融・医療 | EAL3-4 | 3000-5000万円 | 9-12ヶ月 |
| 政府・防衛 | EAL4+ | 5000万円以上 | 12ヶ月以上 |

## 8. 理解度確認クイズ（4択問題20問）

### 問題1
CCの正式名称として正しいものは次のうちどれか？

- A) Computer Criteria
- B) Common Criteria
- C) Communication Criteria
- D) Certification Criteria

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
CCはCommon Criteria（コモンクライテリア）の略称です。情報セキュリティ製品の評価・認証に関する国際標準（ISO/IEC 15408）として定められています。<br>
<br>
Aが間違いの理由：Computer Criteriaという用語は存在しません<br>
Cが間違いの理由：通信に特化した基準ではありません<br>
Dが間違いの理由：認証だけでなく評価も含む包括的な基準です
</details>

### 問題2
EALの段階数として正しいものは次のうちどれか？

- A) 5段階
- B) 6段階
- C) 7段階
- D) 10段階

<details>
<summary>解答</summary>
<strong>正解: C</strong><br>
EAL（Evaluation Assurance Level）は7段階（EAL1〜EAL7）で定義されています。数字が大きいほど評価の深さと厳密さが増します。<br>
<br>
Aが間違いの理由：5段階は少なすぎます<br>
Bが間違いの理由：6段階ではありません<br>
Dが間違いの理由：10段階は多すぎます
</details>

### 問題3
商用開発で現実的に達成可能な最高のEALレベルは次のうちどれか？

- A) EAL2
- B) EAL3
- C) EAL4
- D) EAL7

<details>
<summary>解答</summary>
<strong>正解: C</strong><br>
EAL4は「系統的設計、テスト、レビュー」のレベルで、商用開発において現実的なコストで達成可能な最高レベルとされています。これより上のレベルは形式的手法が必要となり、コストが急激に増大します。<br>
<br>
Aが間違いの理由：EAL2は基本的なレベルです<br>
Bが間違いの理由：EAL3も商用で可能ですが、最高レベルではありません<br>
Dが間違いの理由：EAL7は形式的検証が必要で、極めて高コストです
</details>

- D) 用紙サイズ

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
デジタル複合機のCC評価では、HDD等に残存するデータの保護機能が重視されます。コピー、スキャン、FAXデータが不正にアクセスされないようにする必要があります。<br>
<br>
Aが間違いの理由：印刷速度は性能であってセキュリティではありません<br>
Cが間違いの理由：省エネはセキュリティ評価の対象外です<br>
Dが間違いの理由：用紙サイズは機能仕様でセキュリティとは無関係です
</details>

### 問題15
金融機関がATMシステムにCC認証製品を採用した場合の効果として最も期待されるものは次のうちどれか？

- B) カード偽造対策の信頼性向上
- C) 電気代の削減
- D) 設置スペースの削減

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
金融機関がCC認証製品を採用する主な目的は、カード偽造や不正アクセスに対するセキュリティ対策の信頼性向上です。第三者評価により、対策の有効性が保証されます。<br>
<br>
Aが間違いの理由：処理速度はセキュリティ評価と直接関係ありません<br>
Cが間違いの理由：電気代はCC評価の対象外です<br>
Dが間違いの理由：物理的なサイズは評価対象ではありません
</details>

### 問題16
CC評価を取得していない製品と比較した場合のデメリットとして最も大きいものは次のうちどれか？

- A) 製品価格が高くなる
- B) 操作が複雑になる
- C) 保守が困難になる
- D) 性能が低下する

<details>
<summary>解答</summary>
<strong>正解: A</strong><br>
CC評価取得には多額のコスト（評価費用、文書作成、専門人材等）がかかるため、その分が製品価格に反映され、高価になる傾向があります。<br>
<br>
Bが間違いの理由：セキュリティ機能により若干複雑になる可能性はありますが、主要なデメリットではありません<br>
Cが間違いの理由：保守性は直接的には影響を受けません<br>
Dが間違いの理由：性能への影響は限定的です
</details>

<br>
Aが間違いの理由：競合動向も重要ですが、顧客要求が最優先です<br>
Cが間違いの理由：評価機関の場所は重要な要因ではありません<br>
Dが間違いの理由：製品の色はセキュリティと無関係です
</details>

## 9. 専門用語集

このスライドで使用された専門用語について、アルファベット順・50音順で解説します。

### アルファベット

**CC (Common Criteria)**
- **読み方**: シーシー、コモンクライテリア
- **意味**: 情報セキュリティ製品の評価・認証に関する国際標準（ISO/IEC 15408）。IT製品のセキュリティ機能の信頼性を第三者が評価するための基準
- **関連用語**: ISO/IEC 15408、CCRA、EAL

**CCRA (Common Criteria Recognition Arrangement)**
- **読み方**: シーシーアールエー
- **意味**: コモンクライテリア評価結果の国際相互承認協定。加盟国間でCC認証結果を相互に承認する仕組み
- **関連用語**: CC、相互承認、国際協定

**CEM (Common Evaluation Methodology)**
- **読み方**: セム
- **意味**: CC評価の実施方法を定めた文書。評価者が従うべき評価手順を詳細に規定
- **関連用語**: CC、評価手法、ISO/IEC 18045

**EAL (Evaluation Assurance Level)**
- **読み方**: イーエーエル、イアル
- **意味**: 評価保証レベル。CC評価の深さと厳密さを示す7段階のレベル（EAL1〜EAL7）
- **関連用語**: CC、評価レベル、保証

**FIPS 140-2**
- **読み方**: フィップス140-2
- **意味**: 米国連邦情報処理標準の暗号モジュールセキュリティ要件。CCと併用されることが多い
- **関連用語**: 暗号モジュール、NIST、セキュリティ要件

**IPA (Information-technology Promotion Agency)**
- **読み方**: アイピーエー
- **意味**: 情報処理推進機構。日本におけるCC認証機関として機能し、JISECを運営
- **関連用語**: JISEC、認証機関、日本

**ISO/IEC 15408**
- **読み方**: アイエスオー/アイイーシー 15408
- **意味**: CCの国際標準規格番号。情報技術セキュリティ評価基準を定めた国際標準
- **関連用語**: CC、国際標準、ISO

**JISEC (Japan Information Technology Security Evaluation and Certification Scheme)**
- **読み方**: ジェイアイセック
- **意味**: 日本のITセキュリティ評価及び認証制度。IPAが運営するCC認証制度
- **関連用語**: IPA、CC認証、日本

**PP (Protection Profile)**
- **読み方**: ピーピー、プロテクションプロファイル
- **意味**: 特定の製品カテゴリに共通するセキュリティ要求事項を定義した文書
- **関連用語**: セキュリティ要件、製品カテゴリ、CC

**ST (Security Target)**
- **読み方**: エスティー、セキュリティターゲット
- **意味**: 評価対象製品のセキュリティ仕様を記述した文書。開発者が作成し、評価の基礎となる
- **関連用語**: セキュリティ仕様、評価文書、TOE

**TOE (Target of Evaluation)**
- **読み方**: ティーオーイー
- **意味**: 評価対象。CC評価の対象となるIT製品、システム、またはその一部
- **関連用語**: 評価対象、製品、システム

### あ行

**暗号モジュール（あんごうモジュール）**
- **意味**: 暗号処理を実行するハードウェア、ソフトウェア、またはその組み合わせ。CC評価では重要な評価対象
- **関連用語**: FIPS 140-2、暗号機能、セキュリティモジュール

### か行

**拡張コンポーネント（かくちょうコンポーネント）**
- **意味**: 標準的なCC要件に追加される特別なセキュリティ要件。EAL4+などの「+」で示される
- **関連用語**: EAL+、追加要件、セキュリティ機能

**監査機能（かんさきのう）**
- **意味**: システムの動作やアクセスを記録・追跡する機能。CC評価で重要な評価項目の一つ
- **関連用語**: ログ機能、アクセス記録、セキュリティ監査

**形式的手法（けいしきてきしゅほう）**
- **意味**: 数学的な手法を用いてシステムの正しさを証明する方法。EAL7で必須となる
- **関連用語**: 数学的証明、形式的検証、EAL7

### さ行

**サイドチャネル攻撃（サイドチャネルこうげき）**
- **意味**: 暗号デバイスの物理的な情報（電力消費、電磁波など）から秘密情報を推測する攻撃
- **関連用語**: 物理攻撃、スマートカード、耐タンパー性

**準形式的手法（じゅんけいしきてきしゅほう）**
- **意味**: 部分的に数学的手法を用いる設計・検証方法。EAL5、EAL6で使用される
- **関連用語**: 準形式的設計、EAL5、EAL6

**脆弱性分析（ぜいじゃくせいぶんせき）**
- **意味**: 製品やシステムのセキュリティ上の弱点を体系的に分析すること。EAL2以上で要求される
- **関連用語**: セキュリティ評価、侵入テスト、リスク分析

**セキュリティ機能要件（セキュリティきのうようけん）**
- **意味**: TOEが満たすべきセキュリティ機能の要求事項。CCの中核的な概念
- **関連用語**: SFR、機能要件、セキュリティ要求

**セキュリティ保証要件（セキュリティほしょうようけん）**
- **意味**: セキュリティ機能が正しく実装されていることを保証するための要求事項
- **関連用語**: SAR、保証要件、EAL

### た行

**第三者評価（だいさんしゃひょうか）**
- **意味**: 開発者や利用者から独立した評価機関による客観的な評価。CCの基本原則
- **関連用語**: 独立評価、評価機関、客観性

**耐タンパー性（たいタンパーせい）**
- **意味**: 物理的な攻撃や解析に対する耐性。スマートカード等で重要な特性
- **関連用語**: 物理的保護、タンパーエビデンス、セキュリティ

### な行

**認証機関（にんしょうきかん）**
- **意味**: 評価結果を審査し、認証書を発行する機関。日本ではIPA/JISECが該当
- **関連用語**: 認証書、JISEC、IPA

**認証書（にんしょうしょ）**
- **意味**: CC評価に合格した製品に対して発行される証明書。国際的に有効
- **関連用語**: CC認証、認証機関、CCRA

### は行

**評価機関（ひょうかきかん）**
- **意味**: CC評価を実施する第三者機関。認定を受けた専門機関が実施
- **関連用語**: 評価施設、第三者評価、JISEC

**評価証拠（ひょうかしょうこ）**
- **意味**: 評価の根拠となる文書、テスト結果、分析報告書などの資料
- **関連用語**: 評価文書、エビデンス、評価資料

**フォルト攻撃（フォルトこうげき）**
- **意味**: デバイスに意図的に誤動作を起こさせて秘密情報を取得する攻撃手法
- **関連用語**: 物理攻撃、グリッチ攻撃、耐タンパー性

### ま行

**モジュール認証（モジュールにんしょう）**
- **意味**: 製品全体ではなく、特定のセキュリティモジュール単位での認証
- **関連用語**: 暗号モジュール、部分評価、FIPS 140-2

### ら行

**ライフサイクル（ライフサイクル）**
- **意味**: 製品の開発から廃棄までの全過程。CC評価では開発ライフサイクルの管理も評価対象
- **関連用語**: 開発プロセス、構成管理、保守

**リスク分析（リスクぶんせき）**
- **意味**: セキュリティ上の脅威と脆弱性を分析し、リスクを評価すること
- **関連用語**: 脅威分析、脆弱性評価、セキュリティリスク

---

**専門用語集作成時の注意点:**
- **技術的正確性**: CC関連の技術定義は国際標準に準拠
- **実務的文脈**: 実際の評価・認証現場での使われ方も含めて説明
- **英語併記**: 原語がある場合は英語も併記し、読み方も明記
- **関連技術との関係**: 他のセキュリティ標準や概念との関係も明記
