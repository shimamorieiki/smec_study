# リフト&シフトについて

## 概要
リフト&シフト（Lift and Shift）は、既存のオンプレミスシステムをクラウド環境へ移行する際の代表的な手法の一つです。アプリケーションのアーキテクチャや機能を大幅に変更することなく、現状のまま（As-Is）クラウド環境へ移行することを特徴とします。「リホスティング」とも呼ばれ、クラウド移行の第一歩として多くの企業が採用している手法です。

## 1. 基本概念・仕組み

### リフト&シフトの定義
- **定義**: 既存のアプリケーションやシステムを、アーキテクチャの変更を最小限に抑えながらクラウド環境へ移行する手法
- **動作原理**: オンプレミス環境で動作しているシステムを、そのままクラウド上の仮想マシン（IaaS）に移動させる
- **特徴**: 短期間での移行が可能で、リスクが比較的低い

### クラウド移行手法との関係
- **従来のシステム更改との違い**: ハードウェアの更新や大規模な改修を伴わない
- **改善点**: 物理的な制約から解放され、スケーラビリティが向上
- **限界**: クラウドネイティブな機能を十分に活用できない

## 2. クラウド移行手法の分類

### 7つのRによる分類
クラウド移行戦略は「7つのR」として体系化されています。

### リフト&シフト（Rehost）
**特徴:**
- アプリケーションの変更なし
- IaaS環境への単純移行
- 移行期間が最短

**算出方法:**
```
移行工数 = システム規模 × 複雑度係数 × 移行難易度
（複雑度係数: 0.5〜1.0、移行難易度: 1.0〜2.0）
```

**📊 具体的な計算例**
**例: 中規模ECサイトの移行**
- システム規模: 100人月相当
- 複雑度係数: 0.7（標準的なWebアプリケーション）
- 移行難易度: 1.2（データベース含む）

**ステップ1: 基本工数の算出**
```
基本工数 = 100 × 0.7 × 1.2 = 84人月
```

**ステップ2: リフト&シフトによる工数削減**
```
実際の移行工数 = 84 × 0.3（リフト&シフト係数） = 25.2人月
```

**結果: 約25人月で移行可能**

💡 **実際の現場では**: テスト期間や並行稼働期間も考慮して、余裕を持った計画を立てることが重要

### リプラットフォーム（Replatform）
**特徴:**
- 最小限のアプリケーション変更
- PaaSサービスの部分的活用
- データベースのマネージドサービス化

**移行例:**
- オンプレミスのOracleデータベース → Amazon RDS for Oracle
- 自社運用のメールサーバー → クラウドメールサービス

### リファクタリング（Refactor）
**特徴:**
- アプリケーションの大幅な改修
- クラウドネイティブ化
- マイクロサービス化

### その他の手法
- **Repurchase（リパーチェス）**: SaaSへの置き換え
- **Retire（リタイア）**: 不要システムの廃止
- **Retain（リテイン）**: オンプレミス維持
- **Relocate（リロケート）**: VMware環境の移行

## 3. 移行プロセスの詳細

### 移行準備フェーズ
#### 現状調査（Assessment）
- **ハードウェア構成**: CPU、メモリ、ストレージ容量の把握
- **ソフトウェア構成**: OS、ミドルウェア、アプリケーションのバージョン
- **依存関係**: システム間連携、外部接続の洗い出し
- **性能要件**: レスポンスタイム、スループットの測定

#### 移行計画策定
1. **優先順位の決定**
   - ビジネスクリティカル度
   - 技術的複雑度
   - 依存関係

2. **移行方式の選択**
   - ビッグバン方式: 一括移行
   - 段階的移行: システムを分割して順次移行
   - ハイブリッド方式: 重要システムは段階的、その他は一括

### 移行実施フェーズ
#### データ移行の手法
- **オンライン移行**: サービス稼働中の移行
- **オフライン移行**: サービス停止を伴う移行
- **ハイブリッド移行**: 初期は大量データをオフライン、差分をオンライン

#### 具体的な移行ツール
```bash
# AWS Server Migration Service (SMS)の例
aws sms create-replication-job \
  --server-id s-12345678 \
  --seed-replication-time 2024-01-01T00:00:00Z \
  --frequency 24 \
  --run-once
```

## 4. 実装例・適用事例

### 基本的な移行パターン
```yaml
# Terraformによるリフト&シフト構成例
resource "aws_instance" "web_server" {
  ami           = "ami-0c55b159cbfafe1f0"  # 移行元と同等のOS
  instance_type = "t3.large"               # オンプレミスと同等スペック
  
  # ネットワーク設定
  vpc_security_group_ids = [aws_security_group.web.id]
  subnet_id              = aws_subnet.public.id
  
  # ストレージ設定
  root_block_device {
    volume_type = "gp3"
    volume_size = 100  # オンプレミスと同容量
  }
  
  tags = {
    Name = "Lifted-Web-Server"
    MigrationMethod = "Lift-and-Shift"
  }
}
```

### 実際の適用事例
#### 事例1: 大手小売業A社
- **課題**: データセンターの老朽化、運用コスト増大
- **適用方法**: 
  - 200台の物理サーバーをAWS EC2へ移行
  - VMware vSphereからAWS上のVMware Cloud on AWSへ
- **結果**: 移行期間6ヶ月、ダウンタイム合計4時間
- **効果**: インフラコスト30%削減、災害対策の強化

#### 事例2: 金融機関B社
- **課題**: 法規制対応、セキュリティ強化
- **適用方法**:
  - 基幹系以外のシステムを段階的に移行
  - プライベートクラウドとのハイブリッド構成
- **結果**: 18ヶ月で70%のシステムを移行
- **効果**: セキュリティ監査工数50%削減

## 5. メリット・デメリット

### メリット
**1. 短期間での移行が可能**
- **理由**: アプリケーション改修が不要
- **効果**: 3〜6ヶ月での移行実現（従来手法の1/3）
- **具体例**: Webアプリケーション100台規模で4ヶ月完了

**2. 移行リスクの最小化**
- **理由**: アーキテクチャ変更なし
- **効果**: 動作検証工数の削減
- **具体例**: 機能テストのみで移行可能（回帰テスト不要）

**3. 即座なクラウドメリットの享受**
- **理由**: インフラの柔軟性向上
- **効果**: スケーリング、DR対策の実現
- **具体例**: 繁忙期のサーバー台数を2倍に自動拡張

### デメリット
**1. クラウドネイティブ機能の未活用**
- **理由**: 従来型アーキテクチャの維持
- **影響**: コスト最適化の限界
- **対策**: 段階的なリファクタリング計画

**2. 運用コストの最適化不足**
- **理由**: オンプレミス前提の設計
- **影響**: 過剰なリソース確保
- **対策**: 移行後のライトサイジング

**3. 技術的負債の持ち越し**
- **理由**: 既存の問題点も移行
- **影響**: 保守性の課題継続
- **対策**: 移行後の継続的改善

## 6. 選択・導入の指針

### 移行手法選択の基準
| 観点 | リフト&シフト | リプラットフォーム | リファクタリング |
|------|--------------|------------------|----------------|
| 移行期間 | ◎（3-6ヶ月） | ○（6-12ヶ月） | △（12ヶ月以上） |
| 移行コスト | ◎（低） | ○（中） | △（高） |
| リスク | ◎（低） | ○（中） | △（高） |
| クラウド最適化 | △（低） | ○（中） | ◎（高） |
| 運用コスト削減 | △（10-20%） | ○（20-40%） | ◎（40%以上） |

### 適用判断フローチャート
1. **システムの寿命は3年以上？**
   - Yes → 次の判断へ
   - No → リタイア検討

2. **大規模な機能追加予定あり？**
   - Yes → リファクタリング推奨
   - No → 次の判断へ

3. **移行期限は6ヶ月以内？**
   - Yes → リフト&シフト推奨
   - No → リプラットフォーム検討

4. **クラウド運用経験は豊富？**
   - Yes → リプラットフォーム可能
   - No → リフト&シフトから開始

### 問題1
リフト&シフトの最も適切な説明はどれか？

- A) アプリケーションを完全に作り直してクラウドに移行する手法
- B) 既存システムをほぼそのままクラウド環境に移行する手法
- C) SaaSサービスに置き換える手法
- D) オンプレミスとクラウドを併用する手法

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
リフト&シフトは、既存のアプリケーションやシステムをアーキテクチャの変更を最小限に抑えながらクラウド環境へ移行する手法です。<br>
<br>

Dが間違いの理由：併用はハイブリッドクラウドの説明<br>
<br>

<details>
<summary>解答</summary>

## 9. 専門用語集

このドキュメントで使用された専門用語について、アルファベット順・50音順で解説します。

### アルファベット

**AWS (Amazon Web Services)**
- **読み方**: エーダブリューエス
- **意味**: Amazon.comが提供するクラウドコンピューティングサービスの総称。EC2、S3、RDSなど200以上のサービスを提供
- **関連用語**: EC2, S3, RDS, CloudFormation

**BYOL (Bring Your Own License)**
- **読み方**: ビーワイオーエル
- **意味**: 既存のソフトウェアライセンスをクラウド環境でも使用できる仕組み
- **関連用語**: ライセンスモビリティ、ライセンス込みインスタンス

**CDC (Change Data Capture)**
- **読み方**: シーディーシー
- **意味**: データベースの変更を検知し、リアルタイムで別のシステムに反映する技術
- **関連用語**: データレプリケーション、オンライン移行

**DR (Disaster Recovery)**
- **読み方**: ディーアール
- **意味**: 災害復旧。システム障害や災害発生時にシステムを復旧させるための計画や仕組み
- **関連用語**: RTO, RPO, バックアップ

**IaaS (Infrastructure as a Service)**
- **読み方**: イアース、アイアース
- **意味**: クラウドサービスモデルの一つ。仮想マシン、ストレージ、ネットワークなどのインフラを提供
- **関連用語**: PaaS, SaaS, クラウドサービスモデル

**PaaS (Platform as a Service)**
- **読み方**: パース
- **意味**: アプリケーション実行環境やデータベースなどのプラットフォームを提供するクラウドサービス
- **関連用語**: IaaS, SaaS, マネージドサービス

**RDS (Relational Database Service)**
- **読み方**: アールディーエス
- **意味**: AWSが提供するマネージド型リレーショナルデータベースサービス
- **関連用語**: Aurora, マネージドサービス

**SaaS (Software as a Service)**
- **読み方**: サース
- **意味**: ソフトウェアをクラウド上のサービスとして提供する形態
- **関連用語**: Microsoft 365, Salesforce

**SMS (Server Migration Service)**
- **読み方**: エスエムエス
- **意味**: AWSが提供するサーバー移行サービス。オンプレミスのVMをAWSに移行
- **関連用語**: CloudEndure, Migration Hub

**TCO (Total Cost of Ownership)**
- **読み方**: ティーシーオー
- **意味**: システムの導入から運用、廃棄までの総所有コスト
- **関連用語**: ROI, コスト最適化

**VM (Virtual Machine)**
- **読み方**: ブイエム
- **意味**: 仮想マシン。物理サーバー上で動作する仮想的なコンピューター
- **関連用語**: ハイパーバイザー、仮想化

### あ行

**アセスメント**
- **読み方**: アセスメント
- **意味**: 現状調査・評価。移行前にシステムの現状を詳細に調査すること
- **関連用語**: 移行計画、現状分析

**オートスケーリング**
- **読み方**: オートスケーリング
- **意味**: 負荷に応じて自動的にサーバー台数を増減させる機能
- **関連用語**: スケーラビリティ、弾力性

**オンプレミス**
- **読み方**: オンプレミス
- **意味**: 自社でサーバーやネットワーク機器を保有・運用する形態
- **関連用語**: データセンター、クラウド

### か行

**クラウドネイティブ**
- **読み方**: クラウドネイティブ
- **意味**: クラウド環境に最適化されたアプリケーション設計・開発手法
- **関連用語**: マイクロサービス、コンテナ、サーバーレス

**コンテナ**
- **読み方**: コンテナ
- **意味**: アプリケーションと実行環境をパッケージ化する技術
- **関連用語**: Docker, Kubernetes

- **関連用語**: 可用性、SLA

**ハイブリッドクラウド**
- **読み方**: ハイブリッドクラウド

- **関連用語**: モノリシック、API

- **関連用語**: フルマネージド、セルフマネージド

- **意味**: 適切なリソースサイズに調整すること
- **関連用語**: コスト最適化、リソース最適化

- **意味**: アプリケーションの内部構造を改善する作業
- **関連用語**: モダナイゼーション、再構築
