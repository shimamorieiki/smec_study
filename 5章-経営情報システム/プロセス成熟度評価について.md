# プロセス成熟度評価について

## 概要
プロセス成熟度評価は、組織のソフトウェア開発やシステム開発プロセスがどの程度成熟しているかを評価するための体系的なアプローチです。特にCMM（Capability Maturity Model：能力成熟度モデル）とCMMI（Capability Maturity Model Integration：統合能力成熟度モデル）は、世界的に広く採用されている評価フレームワークです。これらのモデルは、組織のプロセス改善を支援し、品質向上、生産性向上、リスク低減を実現することを目的としています。

## 1. 基本概念・仕組み

### プロセス成熟度評価の核となる概念
- **定義**: 組織のプロセスが定義され、管理され、測定され、制御され、効果的である度合いを評価する体系的手法
- **動作原理**: 段階的な成熟度レベルを設定し、各レベルに必要な特性や活動を定義することで、組織の現状を評価し改善目標を明確化
- **特徴**: 
  - 段階的改善アプローチ（一度に全てを改善するのではなく、段階的に改善）
  - プロセス重視（個人の能力ではなく、組織のプロセスに焦点）
  - 継続的改善（一度達成したレベルを維持し、さらなる向上を目指す）

### 関連技術との関係
- **従来技術との違い**: 品質管理が製品に焦点を当てるのに対し、プロセス成熟度評価はプロセス自体の品質に焦点
- **改善点**: 属人的な品質管理から組織的・体系的な品質管理への移行を実現
- **限界**: プロセスの成熟度が高いことと、製品の品質が高いことは必ずしも一致しない

## 2. 主要モデルの種類・分類

### 分類軸
プロセス成熟度評価モデルは、適用範囲、評価方法、成熟度の表現方法によって分類されます。

### CMM（Capability Maturity Model）
**特徴:**
- 1991年にカーネギーメロン大学のSEI（Software Engineering Institute）が開発
- ソフトウェア開発プロセスに特化
- 5段階の成熟度レベルで評価

**成熟度レベル:**
```
レベル1：初期段階（Initial）
- プロセスが場当たり的で混沌とした状態
- 成功は個人の英雄的な努力に依存
- スケジュールやコストの予測が困難

レベル2：反復可能（Repeatable）
- 基本的なプロジェクト管理プロセスが確立
- 過去の成功経験を繰り返すことが可能
- 要求管理、プロジェクト計画、構成管理などが実施

レベル3：定義済み（Defined）
- 組織標準プロセスが確立され文書化
- すべてのプロジェクトで標準プロセスをテーラリング
- トレーニングプログラムが実施

レベル4：管理された（Managed）
- プロセスと製品品質の詳細な測定が実施
- 定量的な管理目標が設定
- プロセスのばらつきが制御される

レベル5：最適化（Optimizing）
- 継続的なプロセス改善が組織文化として定着
- 革新的な技術や手法の導入
- 欠陥予防活動の実施
```

**📊 具体的な評価例**
**例: ある中規模ソフトウェア開発企業の評価**
- 評価対象組織: 従業員150名のソフトウェア開発企業
- 評価期間: 3ヶ月

**ステップ1: 現状分析**
```
・プロジェクト管理：Excel管理、標準化なし
・品質管理：レビュー実施率60%、テスト計画なし
・構成管理：Gitは使用しているが、ルールなし
・トレーニング：新人研修のみ、体系化されていない
```

**ステップ2: レベル判定**
```
レベル1の特徴に該当：
- プロセスが属人的
- 品質が個人に依存
- 予測可能性が低い

結論：レベル1（初期段階）
```

**結果: レベル2達成のための改善計画策定**

💡 **実際の現場では**: レベル1からレベル2への移行には通常18-24ヶ月必要。まず要求管理とプロジェクト計画から着手することが推奨される。

### CMMI（Capability Maturity Model Integration）
**特徴:**
- 2000年にSEIがCMMを統合・発展させて開発
- ソフトウェア開発だけでなく、システム開発、サービス、調達など幅広い領域に適用可能
- 段階表現と連続表現の2つの表現方法を提供

**成熟度レベル（段階表現）:**
```
レベル1：初期（Initial）
- プロセスが予測不可能で、反応的な管理
- 作業は完了するが、しばしば予算超過や納期遅延

レベル2：管理された（Managed）
- プロジェクトレベルでプロセスが管理
- 要求管理、プロジェクト計画、測定と分析などの実践

レベル3：定義された（Defined）
- 組織全体で標準プロセスが定義
- より詳細な標準、手順、ツールの使用

レベル4：定量的に管理された（Quantitatively Managed）
- プロセスが測定され制御される
- 統計的手法を用いた品質とプロセス性能の管理

レベル5：最適化している（Optimizing）
- 継続的改善に焦点
- 革新的技術導入とプロセス改善の組織的展開
```

**プロセス領域（Process Areas）:**
- **レベル2**: 要求管理（REQM）、プロジェクト計画（PP）、プロジェクトの監視と制御（PMC）など7領域
- **レベル3**: 要求開発（RD）、技術解（TS）、製品統合（PI）、検証（VER）、妥当性確認（VAL）など11領域
- **レベル4**: 組織プロセス実績（OPP）、定量的プロジェクト管理（QPM）の2領域
- **レベル5**: 組織改革と展開（OID）、原因分析と解決（CAR）の2領域

## 3. 詳細仕様・評価パラメータ

### 重要な評価基準
#### 成熟度レベルの判定基準
- **意味**: 組織がそのレベルのすべてのプロセス領域の目標を達成しているか
- **設定範囲**: レベル1～5の5段階
- **影響**: 高いレベルほど、品質、生産性、予測可能性が向上
- **推奨値**: 多くの組織はレベル3を目標とする

#### プロセス領域の達成度
- **意味**: 各プロセス領域の固有目標（SG）と固有実践（SP）の実施状況
- **設定範囲**: 未実施、部分的実施、十分実施、制度化の4段階
- **影響**: すべての必須プロセス領域が「十分実施」以上でなければ、そのレベルは達成されない
- **推奨値**: 各プロセス領域で「制度化」レベルを目指す

### 評価方法の詳細
#### SCAMPI（Standard CMMI Appraisal Method for Process Improvement）
- **クラスA**: 最も厳密で公式な評価。ベンチマーキングに使用可能
- **クラスB**: 改善機会の特定に焦点。内部評価に適している
- **クラスC**: 簡易評価。ギャップ分析や初期評価に使用

## 4. 実装例・適用事例

### 基本実装（レベル2達成の例）
```
プロジェクト: 要求管理プロセスの確立

1. 要求管理ツールの導入
   - Redmine/JIRAなどの導入
   - 要求項目のテンプレート作成
   - 変更管理ワークフローの定義

2. プロセス定義書の作成
   - 要求受付から承認までのフロー
   - 役割と責任の明確化
   - エスカレーションルール

3. トレーニングの実施
   - 全プロジェクトマネージャー向け研修
   - ツール操作研修
   - プロセス遵守の重要性教育

4. パイロットプロジェクトでの実施
   - 小規模プロジェクトで試行
   - 問題点の洗い出しと改善
   - 成功事例の横展開
```

### 応用実装（レベル3達成の例）
```
組織標準プロセスの確立プロジェクト

1. EPG（Engineering Process Group）の設立
   - プロセス改善専門チームの組成
   - 各部門からの代表者参加
   - 定期的な改善活動の実施

2. 組織標準プロセス資産の整備
   - 開発標準プロセスの文書化
   - プロセステーラリングガイドライン
   - 測定項目と分析手法の標準化
   - レビューチェックリスト
   - テスト計画テンプレート

3. プロセス資産ライブラリの構築
   - SharePointやConfluenceでの一元管理
   - バージョン管理の実施
   - アクセス権限の設定

4. 組織的トレーニングプログラム
   - スキルマップの作成
   - 年間教育計画の策定
   - e-ラーニングシステムの導入
```

### 実際の適用事例
#### 事例1: 大手SIベンダーA社（従業員5,000名）
- **課題**: プロジェクトの失敗率が高く（30%）、赤字プロジェクトが頻発
- **適用方法**: 
  - 2018年：CMMI導入決定、現状分析でレベル1と判定
  - 2019年：レベル2のプロセス領域を段階的に導入
  - 2020年：レベル2達成、レベル3への取り組み開始
  - 2022年：レベル3達成
- **結果**: プロジェクト失敗率が30%から8%に減少
- **効果**: 年間10億円のコスト削減、顧客満足度20%向上

#### 事例2: 中堅ソフトウェア開発B社（従業員300名）
- **課題**: 品質のばらつきが大きく、保守コストが増大
- **適用方法**: 
  - CMMIレベル3を目標に3年計画を策定
  - 品質保証部門を新設し、プロセス改善を推進
  - 全社的な品質メトリクスの収集と分析を開始
- **結果**: 出荷後欠陥密度が70%減少
- **効果**: 保守コストが年間3,000万円削減、新規受注が20%増加

## 5. メリット・デメリット

### メリット
**1. プロセスの標準化と予測可能性の向上**
- **理由**: 明確に定義されたプロセスにより、作業の一貫性が保証される
- **効果**: プロジェクトの成功率向上、スケジュール遵守率の改善
- **具体例**: A社では納期遵守率が60%から92%に向上

**2. 品質の向上と欠陥の削減**
- **理由**: 体系的なレビューとテストプロセスにより、早期に欠陥を発見
- **効果**: 出荷後の欠陥数減少、保守コストの削減
- **具体例**: B社では重大欠陥が80%削減、軽微欠陥も50%削減

**3. 組織能力の向上と競争力強化**
- **理由**: 継続的改善により、組織全体の能力が向上
- **効果**: 新規案件の受注率向上、利益率の改善
- **具体例**: CMMIレベル3認定により、公共案件の入札参加資格を獲得

### デメリット
**1. 導入コストと時間の負担**
- **理由**: プロセス定義、文書化、トレーニング、評価に多大な投資が必要
- **影響**: 初期投資として数千万円、期間として2-3年必要
- **対策**: 段階的導入により、投資を分散。ROIを測定し経営層の理解を得る

**2. 形式主義に陥るリスク**
- **理由**: プロセス遵守が目的化し、本来の目的である品質向上が疎かになる
- **影響**: 書類作成の負担増加、開発スピードの低下
- **対策**: アジャイル開発との融合、必要最小限のドキュメント化

**3. 小規模組織での適用の困難さ**
- **理由**: 限られたリソースで多くのプロセス領域をカバーする必要がある
- **影響**: 人材不足、コスト負担の相対的増大
- **対策**: 重要なプロセス領域に絞った部分適用、外部コンサルタントの活用

## 6. 選択・導入の指針

### モデル選択の基準
| 観点 | CMM | CMMI | その他（ISO 9001等） |
|------|-----|------|---------------------|
| 適用範囲 | △（ソフトウェアのみ） | ◎（幅広い領域） | ○（汎用的） |
| 認知度 | △（過去のモデル） | ◎（業界標準） | ○（一般的） |
| コスト | ○（既存資料多い） | △（評価費用高） | ◎（比較的安価） |
| 習得難易度 | ○（シンプル） | △（複雑） | ◎（理解しやすい） |

### 適用判断フローチャート
1. **組織規模は100名以上か？** 
   - Yes → CMMIフル適用を検討
   - No → 次の判断へ

2. **ソフトウェア開発が主要事業か？**
   - Yes → CMMI-DEVの部分適用を検討
   - No → ISO 9001やアジャイル手法を検討

3. **公共案件や大手企業との取引があるか？**
   - Yes → CMMI認定取得を推奨
   - No → 内部改善のみでも可

## 8. 理解度確認クイズ（4択問題20問）

### 問題1
CMMの正式名称として正しいものはどれか？

- A) Capability Maturity Model
- B) Computer Management Model
- C) Continuous Maturity Method
- D) Corporate Management Model

<details>
<summary>解答</summary>
<strong>正解: A</strong><br>
CMMはCapability Maturity Model（能力成熟度モデル）の略称です。1991年にカーネギーメロン大学のSEIが開発したソフトウェア開発プロセスの成熟度を評価するモデルです。<br>
<br>
Bが間違いの理由：Computer Managementはコンピュータ管理であり、プロセス成熟度とは関係ありません<br>
Cが間違いの理由：Continuous（継続的）ではなくCapability（能力）が正しい<br>
Dが間違いの理由：Corporate（企業）管理ではなく、プロセスの能力に関するモデルです<br>
<br>
【補足】CMMは後にCMMIに統合・発展しましたが、基本的な考え方は引き継がれています。
</details>

### 問題2
CMMIの成熟度レベル2は何と呼ばれるか？

- A) 初期（Initial）
- B) 管理された（Managed）
- C) 定義された（Defined）
- D) 最適化している（Optimizing）

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
CMMIの成熟度レベル2は「管理された（Managed）」です。このレベルでは、プロジェクトレベルでプロセスが管理され、要求管理やプロジェクト計画などが実施されます。<br>
<br>
Aが間違いの理由：初期（Initial）はレベル1です<br>
Cが間違いの理由：定義された（Defined）はレベル3です<br>
Dが間違いの理由：最適化している（Optimizing）はレベル5です<br>
<br>
【補足】レベル2では7つのプロセス領域（要求管理、プロジェクト計画、プロジェクトの監視と制御など）の実践が求められます。
</details>

### 問題3
組織がCMMIレベル3を達成するために必要なプロセス領域の数は？

- A) 7個
- B) 11個
- C) 18個（レベル2の7個＋レベル3の11個）
- D) 22個

<details>
<summary>解答</summary>
<strong>正解: C</strong><br>
CMMIレベル3を達成するには、レベル2の7個のプロセス領域に加えて、レベル3の11個のプロセス領域、合計18個のプロセス領域を実装する必要があります。<br>
<br>
Aが間違いの理由：7個はレベル2のプロセス領域数のみ<br>
Bが間違いの理由：11個はレベル3で新たに追加されるプロセス領域数のみ<br>
Dが間違いの理由：22個はレベル5までの全プロセス領域数<br>
<br>
【補足】各レベルは累積的であり、上位レベルを達成するには下位レベルのすべてのプロセス領域も満たす必要があります。
</details>

### 問題4
CMMとCMMIの主な違いとして正しいものはどれか？

- A) CMMは5段階、CMMIは3段階の成熟度レベル
- B) CMMはソフトウェア開発のみ、CMMIは複数の分野に適用可能
- C) CMMは米国発、CMMIは日本発のモデル
- D) CMMは大企業向け、CMMIは中小企業向け

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
CMMはソフトウェア開発に特化していましたが、CMMIは開発（CMMI-DEV）、サービス（CMMI-SVC）、調達（CMMI-ACQ）など複数の分野に適用可能な統合モデルです。<br>
<br>
Aが間違いの理由：両方とも5段階の成熟度レベルを持っています<br>
Cが間違いの理由：両方ともカーネギーメロン大学のSEI（米国）が開発<br>
Dが間違いの理由：企業規模による区別はなく、適用方法を調整することで様々な規模の組織に適用可能<br>
<br>
【補足】CMMIは2000年にCMMを含む複数の成熟度モデルを統合して作られました。
</details>

### 問題5
プロセス成熟度評価を行う主な目的として最も適切なものは？

- A) 従業員の個人評価を行うため
- B) 競合他社との比較を行うため
- C) 組織のプロセス改善の指針を得るため
- D) 監査機関への報告のため

<details>
<summary>解答</summary>
<strong>正解: C</strong><br>
プロセス成熟度評価の主な目的は、組織の現在のプロセス能力を把握し、改善すべき領域を特定して、体系的なプロセス改善を実施するための指針を得ることです。<br>
<br>
Aが間違いの理由：個人ではなく組織のプロセスを評価するもの<br>
Bが間違いの理由：競合比較は副次的な効果であり、主目的ではない<br>
Dが間違いの理由：監査対応は結果的な効果であり、改善が主目的<br>
<br>
【補足】評価結果は改善計画の策定に使用され、継続的なプロセス改善サイクルの起点となります。
</details>

### 問題6
CMMIレベル2の「要求管理（REQM）」プロセス領域の主な目的は？

- A) 新しい要求を積極的に発掘すること
- B) 要求の変更を防ぐこと
- C) 要求とその変更を管理すること
- D) 要求の優先順位を決定すること

<details>
<summary>解答</summary>
<strong>正解: C</strong><br>
要求管理（REQM）プロセス領域の目的は、プロジェクトの要求を管理し、要求とプロジェクト計画および作業成果物との間の不整合を識別することです。変更管理も含まれます。<br>
<br>

### 問題12

- 平均欠陥密度：2.5個/KLOC
- 標準偏差：0.8個/KLOC
- 管理限界を±2σに設定
次のプロジェクトで欠陥密度が4.2個/KLOCだった場合、どのような判断をすべきか？

- A) 正常範囲内なので問題なし
- B) 管理限界を超えているため、原因分析が必要
- C) データが少ないため判断できない
- D) 平均値を更新すべき

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>

上限 = 2.5 + (2 × 0.8) = 4.1<br>
下限 = 2.5 - (2 × 0.8) = 0.9<br>
4.2 > 4.1 なので管理限界外<br>
<br>
Aが間違いの理由：管理限界を超えているため、正常範囲外<br>
Cが間違いの理由：10プロジェクトのデータは統計的管理を開始するには十分<br>
Dが間違いの理由：異常値を含めて平均を更新すると、管理が甘くなる<br>
<br>

</details>

## 9. 専門用語集

このスライドで使用された専門用語について、アルファベット順・50音順で解説します。

### アルファベット

**CAR (Causal Analysis and Resolution)**
- **読み方**: シーエーアール
- **意味**: 原因分析と解決。欠陥やその他の問題の原因を統計的に分析し、将来の発生を防ぐためのCMMIレベル5のプロセス領域
- **関連用語**: 根本原因分析、欠陥予防

**CMM (Capability Maturity Model)**
- **読み方**: シーエムエム
- **意味**: 能力成熟度モデル。1991年にSEIが開発したソフトウェア開発プロセスの成熟度を5段階で評価するモデル
- **関連用語**: CMMI、プロセス成熟度

**CMMI (Capability Maturity Model Integration)**
- **読み方**: シーエムエムアイ
- **意味**: 統合能力成熟度モデル。CMMを発展させた統合的なプロセス改善モデル。開発、サービス、調達の各分野に対応
- **関連用語**: CMM、プロセス改善、成熟度レベル

**EPG (Engineering Process Group)**
- **読み方**: イーピージー
- **意味**: エンジニアリングプロセスグループ。組織のプロセス改善活動を推進する専門チーム
- **関連用語**: プロセス改善、SEPG

**GP (Generic Practice)**
- **読み方**: ジーピー
- **意味**: 共通実践。CMMIの各プロセス領域に共通して適用される実践。制度化の度合いを示す
- **関連用語**: SP、GG

**OPD (Organizational Process Definition)**
- **読み方**: オーピーディー
- **意味**: 組織プロセス定義。組織の標準プロセスを確立し維持するCMMIレベル3のプロセス領域
- **関連用語**: 標準プロセス、プロセス資産

**PMC (Project Monitoring and Control)**
- **読み方**: ピーエムシー
- **意味**: プロジェクトの監視と制御。プロジェクトの進捗を追跡し、計画からの逸脱を管理するCMMIレベル2のプロセス領域
- **関連用語**: プロジェクト管理、PP

**PP (Project Planning)**
- **読み方**: ピーピー
- **意味**: プロジェクト計画。プロジェクト活動の計画を確立し維持するCMMIレベル2のプロセス領域
- **関連用語**: PMC、プロジェクト管理

**REQM (Requirements Management)**
- **読み方**: レクム
- **意味**: 要求管理。プロジェクトの要求を管理し、不整合を識別するCMMIレベル2のプロセス領域
- **関連用語**: 要求開発、変更管理

**SCAMPI (Standard CMMI Appraisal Method for Process Improvement)**
- **読み方**: スキャンピ
- **意味**: CMMIの標準評価手法。クラスA、B、Cの3種類があり、厳密さと目的が異なる
- **関連用語**: アプレイザル、評価

**SEI (Software Engineering Institute)**
- **読み方**: エスイーアイ
- **意味**: ソフトウェア工学研究所。カーネギーメロン大学に設置され、CMM/CMMIを開発した研究機関
- **関連用語**: カーネギーメロン大学、CMM、CMMI

**SG (Specific Goal)**
- **読み方**: エスジー
- **意味**: 固有目標。各プロセス領域で達成すべき固有の目標
- **関連用語**: SP、GG

**SP (Specific Practice)**
- **読み方**: エスピー
- **意味**: 固有実践。各プロセス領域の固有目標を達成するための具体的な活動
- **関連用語**: SG、GP
