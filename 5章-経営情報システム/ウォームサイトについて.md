# ウォームサイトについて

## 概要
ウォームサイト（Warm Site）は、災害復旧（DR: Disaster Recovery）戦略の一つで、主要な情報システムの運用を継続するためのバックアップ施設です。コストと復旧時間のバランスを考慮した中間的な選択肢として、多くの企業で採用されています。ホットサイトとコールドサイトの中間に位置し、適度な投資で実用的な災害復旧能力を提供します。

## 1. 基本概念・仕組み

### ウォームサイトの定義
- **定義**: 必要なハードウェアと通信回線が設置されているが、本番データの同期は定期的に行われる災害復旧施設
- **動作原理**: 平常時は最小限の稼働状態を維持し、災害発生時に短時間で本番環境として稼働可能な状態に移行
- **特徴**: コストと復旧時間の最適なバランスを実現

### 災害復旧サイトの位置づけ
- **従来の単一拠点運用との違い**: 地理的に離れた場所に代替施設を設置することで、局地的災害のリスクを分散
- **改善点**: ホットサイトより低コストで、コールドサイトより迅速な復旧が可能
- **限界**: リアルタイムでのデータ同期は行わないため、一定のデータロスが発生する可能性

## 2. 種類・分類

### 災害復旧サイトの分類
災害復旧サイトは、準備状態と復旧時間によって以下の3つに分類されます。

### ホットサイト（Hot Site）
**特徴:**
- 本番環境と同等のシステムが常時稼働
- リアルタイムまたは準リアルタイムでデータ同期
- 即座に切り替え可能（数分～数時間）

**算出方法:**
```
年間コスト = 設備費用 + 運用費用 + データ同期費用 + 人件費
          = 初期投資/償却年数 + 月額運用費×12 + 通信費×12 + 常駐要員費
```

**📊 具体的な計算例**
**例: 中規模ECサイトのホットサイト構築**
- サーバー設備: 5,000万円（5年償却）
- 月額運用費: 200万円
- データ同期用専用線: 月額50万円
- 常駐要員: 2名（年間1,200万円）

**ステップ1: 年間設備費用の計算**
```
年間設備費用 = 5,000万円 ÷ 5年 = 1,000万円
```

**ステップ2: 年間総コストの計算**
```
年間総コスト = 1,000万円 + (200万円×12) + (50万円×12) + 1,200万円
            = 1,000万円 + 2,400万円 + 600万円 + 1,200万円
            = 5,200万円
```

**結果: 年間5,200万円のコストで、ほぼ無停止のサービス継続が可能**

💡 **実際の現場では**: 金融機関や大規模ECサイトなど、数分の停止も許されない業務で採用

### ウォームサイト（Warm Site）
**特徴:**
- 必要なハードウェアは設置済み
- OSやミドルウェアは導入済み
- データは定期的にバックアップ
- 復旧時間は数時間～1日程度

**算出方法:**
```
年間コスト = 設備費用 + 保守費用 + バックアップ費用
          = 初期投資/償却年数 + 月額保守費×12 + バックアップ運用費
```

**📊 具体的な計算例**
**例: 製造業の基幹システムのウォームサイト**
- サーバー設備: 2,000万円（5年償却）
- 月額保守費: 30万円
- バックアップシステム: 500万円（5年償却）
- バックアップ運用: 月額10万円

**ステップ1: 年間設備費用の計算**
```
年間設備費用 = (2,000万円 + 500万円) ÷ 5年 = 500万円
```

**ステップ2: 年間総コストの計算**
```
年間総コスト = 500万円 + (30万円×12) + (10万円×12)
            = 500万円 + 360万円 + 120万円
            = 980万円
```

**結果: 年間980万円のコストで、半日程度での業務再開が可能**

💡 **実際の現場では**: 一般的な企業の基幹システムや、数時間の停止が許容される業務で広く採用

### コールドサイト（Cold Site）
**特徴:**
- 建物と基本的なインフラのみ
- ハードウェアの調達から開始
- 復旧時間は数日～数週間

**算出方法:**
```
年間コスト = 施設費用 + 最小限の維持費
          = 賃料 + 基本インフラ維持費
```

**📊 具体的な計算例**
**例: 中小企業のバックアップサイト**
- 施設賃料: 月額20万円
- 電源・空調維持: 月額5万円
- 緊急時機器調達予算: 1,000万円（積立）

**年間総コスト計算**
```
年間総コスト = (20万円×12) + (5万円×12) + (1,000万円÷5年)
            = 240万円 + 60万円 + 200万円
            = 500万円
```

**結果: 年間500万円のコストで、1週間程度での業務再開が可能**

💡 **実際の現場では**: 災害発生頻度が低い地域の企業や、長期間の停止が許容される業務で採用

## 3. 詳細仕様・パラメータ

### ウォームサイト構築の重要パラメータ

#### RTO（Recovery Time Objective）の詳細
- **意味**: 災害発生から業務再開までの目標復旧時間
- **設定範囲**: 2時間～24時間（ウォームサイトの典型的範囲）
- **影響**: RTOが短いほど、より高性能な設備と自動化が必要
- **推奨値**: 業務の重要度により4～12時間

#### RPO（Recovery Point Objective）の詳細
- **意味**: どの時点のデータまで復旧するかの目標
- **設定範囲**: 1時間～24時間（バックアップ頻度に依存）
- **影響**: RPOが短いほど、頻繁なバックアップと高速な転送が必要
- **推奨値**: 日次バックアップで24時間、重要システムは4～6時間

#### データ同期方式の詳細
- **意味**: 本番サイトからウォームサイトへのデータ転送方法
- **選択肢**: 
  - 定期バックアップ転送（日次/時間単位）
  - 差分バックアップ
  - ログシッピング
- **影響**: 同期頻度が高いほどRPOは短縮されるが、コストは増加
- **推奨値**: 重要度に応じて4～12時間間隔

## 4. 実装例・適用事例

### 基本実装
```bash
# ウォームサイトの基本構成例
/warmsite/
├── infrastructure/
│   ├── servers/          # 事前設置済みサーバー
│   ├── network/          # 構成済みネットワーク機器
│   └── storage/          # バックアップストレージ
├── software/
│   ├── os/              # インストール済みOS
│   ├── middleware/      # 設定済みミドルウェア
│   └── applications/    # アプリケーション（未起動）
└── data/
    ├── daily_backup/    # 日次バックアップ
    └── logs/            # 転送ログ
```

### 応用実装
```python
# ウォームサイト自動復旧スクリプトの例
import subprocess
import time
from datetime import datetime

class WarmSiteActivation:
    def __init__(self):
        self.config = self.load_config()
        self.rto_target = 4  # 4時間以内の復旧目標
        
    def activate_warmsite(self):
        start_time = datetime.now()
        
        # Step 1: 最新バックアップの確認
        latest_backup = self.check_latest_backup()
        print(f"最新バックアップ: {latest_backup}")
        
        # Step 2: データリストア
        self.restore_data(latest_backup)
        
        # Step 3: アプリケーション起動
        self.start_applications()
        
        # Step 4: ヘルスチェック
        if self.health_check():
            elapsed = (datetime.now() - start_time).total_seconds() / 3600
            print(f"復旧完了: {elapsed:.1f}時間")
            return elapsed <= self.rto_target
        
        return False
```

### 実際の適用事例

#### 事例1: 大手製造業A社
- **課題**: 東日本大震災で本社システムが停止、復旧に1週間
- **適用方法**: 関西にウォームサイトを構築、6時間ごとの差分バックアップ
- **結果**: その後の災害訓練で8時間での復旧を確認
- **効果**: BCP（事業継続計画）の信頼性が向上、取引先からの評価も改善

#### 事例2: 中堅小売業B社
- **課題**: 年商100億円規模でホットサイトはコスト的に困難
- **適用方法**: クラウドベースのウォームサイトを構築、日次同期
- **結果**: 月額コスト80万円で、12時間以内の復旧体制を確立
- **効果**: 投資対効果の高いBCP実現、保険料も10%削減

## 5. メリット・デメリット

### メリット

**1. コストパフォーマンスの高さ**
- **理由**: ホットサイトの30-50%程度のコストで実用的な復旧能力
- **効果**: 中堅企業でも導入可能な災害対策
- **具体例**: 年間1,000万円程度で基幹システムの保護が可能

**2. 柔軟な運用**
- **理由**: 平常時は他の用途（開発・テスト環境）にも活用可能
- **効果**: 投資の有効活用
- **具体例**: 開発環境として利用し、緊急時に本番環境へ転換

**3. 段階的な投資**
- **理由**: 必要に応じてホットサイトへのアップグレードが可能
- **効果**: 事業成長に合わせた投資計画
- **具体例**: 売上増加に伴い、同期頻度を段階的に向上

### デメリット

**1. データロスの可能性**
- **理由**: リアルタイム同期ではないため、最新データが失われる
- **影響**: RPO分のトランザクションデータの消失
- **対策**: 重要データは別途リアルタイム同期の仕組みを追加

**2. 復旧時間の長さ**
- **理由**: 手動作業が多く、数時間～1日程度必要
- **影響**: その間のビジネス機会損失
- **対策**: 復旧手順の自動化と定期的な訓練実施

**3. 定期的なメンテナンス**
- **理由**: 使用頻度が低いため、動作確認が必要
- **影響**: 年数回の保守作業とコスト
- **対策**: 四半期ごとの動作確認と年1回の総合訓練

## 6. 選択・導入の指針

### DR戦略選択の基準
| 観点 | ホットサイト | ウォームサイト | コールドサイト |
|------|-------------|---------------|---------------|
| 初期投資 | ✕ 高額 | ○ 中程度 | ◎ 低額 |
| 運用コスト | ✕ 高額 | ○ 中程度 | ◎ 低額 |
| 復旧時間 | ◎ 数分～1時間 | ○ 数時間～1日 | ✕ 数日～数週間 |
| データ保護 | ◎ ほぼ完全 | ○ 一定の損失 | △ 大きな損失 |
| 技術的複雑さ | ✕ 高い | ○ 中程度 | ◎ シンプル |

### 適用判断フローチャート
1. **許容停止時間は？**
   - 1時間未満 → ホットサイト推奨
   - 1時間～24時間 → 次の判断へ
   - 24時間以上 → コールドサイトも検討

2. **許容データ損失は？**
   - 1時間未満 → ホットサイト推奨
   - 1時間～24時間 → ウォームサイト推奨
   - 24時間以上 → コールドサイトも検討

3. **年間予算は？**
   - 売上の0.5%以上 → ホットサイト可能
   - 売上の0.1～0.5% → ウォームサイト推奨
   - 売上の0.1%未満 → コールドサイトまたはクラウドDR

## 8. 理解度確認クイズ（4択問題20問）

### 問題1
ウォームサイトの定義として最も適切なものはどれか。

- A) リアルタイムでデータ同期を行い、即座に切り替え可能な施設
- B) 必要なハードウェアと基本ソフトウェアが導入済みで、定期的にデータバックアップを行う施設
- C) 建物と電源設備のみが用意された空の施設
- D) 本番環境と全く同じシステムが常時稼働している施設

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
ウォームサイトは、必要なハードウェアとOS・ミドルウェアなどの基本ソフトウェアが導入済みで、データは定期的なバックアップで同期する施設です。<br>
<br>
Aが間違いの理由：リアルタイム同期と即座の切り替えはホットサイトの特徴<br>
Cが間違いの理由：建物と基本設備のみはコールドサイトの特徴<br>
Dが間違いの理由：本番環境と同じシステムの常時稼働はホットサイトの特徴<br>
<br>
【補足】実務では、ウォームサイトは初期投資と運用コストのバランスが良いため、多くの企業で採用されています。
</details>

### 問題2
RTOが4時間、RPOが6時間と設定されている場合の説明として正しいものはどれか。

- A) 災害発生から4時間以内に復旧し、6時間前のデータまで復元する
- B) 災害発生から6時間以内に復旧し、4時間前のデータまで復元する  
- C) 4時間ごとにバックアップを取り、6時間で復旧する
- D) 6時間ごとにバックアップを取り、4時間で復旧する

<details>
<summary>解答</summary>
<strong>正解: A</strong><br>
RTO（Recovery Time Objective）は復旧時間目標で4時間以内の復旧を、RPO（Recovery Point Objective）は復旧時点目標で6時間前のデータまでの復元を意味します。<br>
<br>
Bが間違いの理由：RTOとRPOの意味が逆になっている<br>
Cが間違いの理由：RTOはバックアップ頻度ではなく復旧時間を示す<br>
Dが間違いの理由：RPOはバックアップ頻度を直接示すものではない<br>
<br>
【補足】実務では、RTOとRPOは業務の重要度と投資可能額のバランスで決定されます。
</details>

### 問題3
年商50億円の企業がウォームサイトに年間1,000万円を投資する場合、売上高に対する投資比率は何%か。

- A) 0.02%
- B) 0.2%
- C) 2%
- D) 20%

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
計算式：(1,000万円 ÷ 50億円) × 100 = (1,000万円 ÷ 5,000,000万円) × 100 = 0.2%<br>
<br>
Aが間違いの理由：計算を1桁間違えている（0.02%は100万円の投資に相当）<br>
Cが間違いの理由：計算を1桁間違えている（2%は1億円の投資に相当）<br>
Dが間違いの理由：計算を2桁間違えている（20%は10億円の投資に相当）<br>
<br>
【補足】一般的に、DR投資は売上高の0.1～0.5%程度が適切とされています。
</details>

### 問題5
災害復旧サイトの分類で、最もコストが高いものから順に並べた場合、正しいものはどれか。

- A) ホットサイト → ウォームサイト → コールドサイト
- B) ウォームサイト → ホットサイト → コールドサイト
- C) コールドサイト → ウォームサイト → ホットサイト
- D) ホットサイト → コールドサイト → ウォームサイト

<details>
<summary>解答</summary>
<strong>正解: A</strong><br>
ホットサイトは常時稼働でリアルタイム同期のため最も高額、ウォームサイトは中間的なコスト、コールドサイトは最小限の設備のため最も低コストです。<br>
<br>
Bが間違いの理由：ホットサイトが最も高額であるべき<br>
Cが間違いの理由：コストの順序が完全に逆<br>
Dが間違いの理由：コールドサイトはウォームサイトより低コスト<br>
<br>
【補足】一般的にホットサイトはウォームサイトの2-3倍、コールドサイトの5-10倍のコストがかかります。
</details>

### 問題6
ウォームサイトでのデータ同期方式として一般的でないものはどれか。

- A) 日次バックアップ
- B) 差分バックアップ
- C) ログシッピング
- D) 同期レプリケーション

<details>
<summary>解答</summary>
<strong>正解: D</strong><br>
同期レプリケーションはリアルタイムでデータを同期する方式で、ホットサイトで使用される技術です。ウォームサイトでは定期的なバックアップが一般的です。<br>
<br>
Aが一般的な理由：日次バックアップは最も基本的なウォームサイトの同期方式<br>
Bが一般的な理由：差分バックアップで転送量を削減しつつ定期同期を実現<br>
Cが一般的な理由：ログシッピングで準リアルタイムに近い同期が可能<br>
<br>
【補足】ウォームサイトでは、RPO要件に応じて適切な同期方式を選択することが重要です。
</details>

### 問題7
製造業の基幹システムでRTO 8時間、RPO 4時間の要件がある場合、最も適切なDR戦略はどれか。

- A) ホットサイト（コストに関わらず最高の可用性を確保）
- B) ウォームサイト（要件を満たしつつコスト最適化）
- C) コールドサイト（最低限のコストで対応）
- D) DR戦略は不要（要件が緩いため）

<details>
<summary>解答</summary>
<strong>正解: B</strong><br>
RTO 8時間、RPO 4時間はウォームサイトで十分対応可能な要件です。ホットサイトは過剰投資となり、コールドサイトでは要件を満たせません。<br>

## 9. 専門用語集

このスライドで使用された技術用語について、アルファベット順・50音順で解説します。

### アルファベット

**BCP (Business Continuity Plan)**
- **読み方**: ビーシーピー
- **意味**: 事業継続計画。災害や事故などの緊急事態が発生した際に、重要業務を継続または早期復旧するための計画
- **関連用語**: BCM（事業継続マネジメント）、BIA（ビジネスインパクト分析）

**BIA (Business Impact Analysis)**
- **読み方**: ビーアイエー
- **意味**: ビジネスインパクト分析。業務中断がビジネスに与える影響を分析し、復旧優先順位を決定するプロセス
- **関連用語**: RTO、RPO、MTPD（最大許容停止時間）

**DR (Disaster Recovery)**
- **読み方**: ディーアール
- **意味**: 災害復旧。災害によってIT システムが被害を受けた場合に、システムを復旧・修復する仕組みや体制
- **関連用語**: DRP（災害復旧計画）、DRサイト

**DRaaS (Disaster Recovery as a Service)**
- **読み方**: ディーラース
- **意味**: クラウドサービスとして提供される災害復旧ソリューション。自社でDRサイトを構築・運用する必要がない
- **関連用語**: IaaS、PaaS、SaaS

**MTPD (Maximum Tolerable Period of Disruption)**
- **読み方**: エムティーピーディー
- **意味**: 最大許容停止時間。業務が停止してからビジネスに深刻な影響が出るまでの時間
- **関連用語**: RTO、RPO

**RPO (Recovery Point Objective)**
- **読み方**: アールピーオー
- **意味**: 目標復旧時点。災害発生時にどの時点のデータまで復旧するかの目標値
- **関連用語**: RTO、バックアップ頻度

**RTO (Recovery Time Objective)**
- **読み方**: アールティーオー
- **意味**: 目標復旧時間。災害発生からシステム復旧までの目標時間
- **関連用語**: RPO、MTPD

**SLA (Service Level Agreement)**
- **読み方**: エスエルエー
- **意味**: サービスレベル契約。サービス提供者と利用者間で交わされる、サービス品質に関する合意
- **関連用語**: SLO（サービスレベル目標）

### あ行

**ウォームサイト（Warm Site）**
- **読み方**: うぉーむさいと
- **意味**: 必要なハードウェアと基本ソフトウェアが設置され、定期的にデータバックアップを行う災害復旧施設
- **関連用語**: ホットサイト、コールドサイト

### か行

**コールドサイト（Cold Site）**
- **読み方**: こーるどさいと
- **意味**: 建物と基本的なインフラのみが用意された災害復旧施設。機器は災害後に調達
- **関連用語**: ホットサイト、ウォームサイト

**コンテナオーケストレーション（Container Orchestration）**
- **読み方**: こんてなおーけすとれーしょん
- **意味**: 複数のコンテナの展開、管理、スケーリング、ネットワーキングを自動化する技術
- **関連用語**: Kubernetes、Docker Swarm

### さ行

**差分バックアップ（Differential Backup）**
- **読み方**: さぶんばっくあっぷ
- **意味**: 前回のフルバックアップ以降に変更されたデータのみをバックアップする方式
- **関連用語**: フルバックアップ、増分バックアップ

**冗長化（Redundancy）**
- **読み方**: じょうちょうか
- **意味**: システムの一部に障害が発生しても全体の機能を維持できるよう、予備を用意すること
- **関連用語**: 可用性、フェイルオーバー

### た行

**同期レプリケーション（Synchronous Replication）**
- **読み方**: どうきれぷりけーしょん
- **意味**: データの書き込みを主系と待機系で同時に行う複製方式。データの完全性は保証されるが性能への影響がある
- **関連用語**: 非同期レプリケーション

### な行

**二重化（Duplication）**
- **読み方**: にじゅうか
- **意味**: システムや機器を2つ用意し、一方に障害が発生しても他方で処理を継続できるようにすること
- **関連用語**: 冗長化、ミラーリング

### は行

**バックアップ（Backup）**
- **読み方**: ばっくあっぷ
- **意味**: データやシステムの複製を作成し、障害時に復元できるようにすること
- **関連用語**: リストア、アーカイブ

**非同期レプリケーション（Asynchronous Replication）**
- **読み方**: ひどうきれぷりけーしょん
- **意味**: 主系への書き込み完了後に待機系へデータを転送する複製方式。性能への影響は小さいがデータロスの可能性がある
- **関連用語**: 同期レプリケーション

**フェイルオーバー（Failover）**
- **読み方**: ふぇいるおーばー
- **意味**: 稼働中のシステムに障害が発生した際に、自動的に待機系システムに切り替える機能
- **関連用語**: フェイルバック、切り替え

**ホットサイト（Hot Site）**
- **読み方**: ほっとさいと
- **意味**: 本番環境と同等のシステムが常時稼働し、リアルタイムでデータ同期を行う災害復旧施設
- **関連用語**: ウォームサイト、コールドサイト

### ら行

**リストア（Restore）**
- **読み方**: りすとあ
- **意味**: バックアップからデータやシステムを復元すること
- **関連用語**: バックアップ、リカバリ

**ログシッピング（Log Shipping）**
- **読み方**: ろぐしっぴんぐ
- **意味**: データベースのトランザクションログを定期的に転送し、待機系に適用する方式
- **関連用語**: レプリケーション、ミラーリング
