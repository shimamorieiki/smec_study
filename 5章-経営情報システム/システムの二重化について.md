# システムの二重化について

## 概要
システムの二重化（System Redundancy）とは、システムの信頼性・可用性を向上させるために、システムやその構成要素を複数用意する技術です。単一障害点（SPOF: Single Point of Failure）を排除し、一部に障害が発生しても全体のサービスを継続できるようにすることが目的です。高可用性（HA: High Availability）を実現するための重要な技術として、ミッションクリティカルなシステムで広く採用されています。

## 1. 基本概念・仕組み

### システム冗長化の定義
- **定義**: システムやその構成要素を複数用意し、一部に障害が発生してもサービスを継続できるようにする技術
- **動作原理**: 複数のシステムが連携し、障害時には正常なシステムが処理を引き継ぐ
- **特徴**: 高い可用性、障害耐性、無停止運用の実現

### 冗長化の必要性
- **従来の単一システムの問題点**: 
  - 障害発生時にサービス全体が停止
  - メンテナンス時にサービス停止が必要
  - 処理能力の限界が明確
- **改善点**: 
  - 障害時の自動切り替え
  - 無停止メンテナンスの実現
  - 処理能力の動的な拡張
- **限界**: 
  - コストの増大
  - システムの複雑化
  - 管理負荷の増加

## 2. 種類・分類

### 冗長化方式による分類
システムの二重化は、処理方式や待機状態により以下のように分類されます。

### デュプレックスシステム（Duplex System）
**特徴:**
- 主系（現用系）と待機系の2つのシステムで構成
- 通常時は主系のみが稼働し、待機系はスタンバイ状態
- 障害発生時に待機系に切り替え

**算出方法:**
```
システム稼働率 = 1 - (1 - 単体稼働率)²
切替時間 = 障害検知時間 + 切替処理時間 + システム起動時間
```

**📊 具体的な計算例**
**例: 金融機関のオンラインバンキングシステム**
- 単体システム稼働率: 99.0%（年間停止時間：約87.6時間）
- 障害検知時間: 30秒
- 切替処理時間: 60秒
- システム起動時間: 120秒

**ステップ1: システム稼働率の計算**
```
システム稼働率 = 1 - (1 - 0.99)²
                = 1 - (0.01)²
                = 1 - 0.0001
                = 0.9999
                = 99.99%
```

**ステップ2: 年間停止時間の計算**
```
年間停止時間 = 365日 × 24時間 × (1 - 0.9999)
            = 8760時間 × 0.0001
            = 0.876時間
            = 約52.6分
```

**結果: 稼働率が99.0%から99.99%に向上し、年間停止時間が87.6時間から52.6分に短縮**

💡 **実際の現場では**: 待機系のハードウェアは定期的に動作確認が必要。また、データの同期方法（リアルタイム/バッチ）により復旧時間が変わるため、RPO（Recovery Point Objective）とRTO（Recovery Time Objective）を明確に定義することが重要です。

### デュアルシステム（Dual System）
**特徴:**
- 2つのシステムが同時に同じ処理を実行
- 結果を照合し、一致した場合のみ処理を確定
- 高い信頼性と即時性を実現

**算出方法:**
```
処理遅延時間 = 処理時間 + 照合時間
システム信頼性 = 1 - (誤り率)²
```

**📊 具体的な計算例**
**例: 航空管制システム**
- 単体処理時間: 100ms
- 照合処理時間: 20ms
- 単体システム誤り率: 0.001%（10⁻⁵）

**ステップ1: 処理遅延時間の計算**
```
処理遅延時間 = 100ms + 20ms
            = 120ms
```

**ステップ2: システム信頼性の計算**
```
システム信頼性 = 1 - (10⁻⁵)²
              = 1 - 10⁻¹⁰
              = 0.9999999999
              = 99.99999999%
```

**結果: 処理時間は20%増加するが、信頼性は飛躍的に向上**

💡 **実際の現場では**: 照合不一致時の処理方法（多数決、再処理、システム停止）を事前に定義することが重要。また、両系の時刻同期が必須となるため、高精度な時刻同期システム（GPS、NTP）の導入が必要です。

### ロードシェアシステム（Load Share System）
**特徴:**
- 複数のシステムが負荷を分散して処理
- 障害時は残りのシステムで処理を継続
- スケーラビリティと可用性を両立

**算出方法:**
```
処理能力 = 単体処理能力 × システム数 × 負荷分散効率
障害時処理能力 = 処理能力 × (稼働システム数 / 全システム数)
```

**📊 具体的な計算例**
**例: Webアプリケーションサーバー（4台構成）**
- 単体処理能力: 1000リクエスト/秒
- システム数: 4台
- 負荷分散効率: 90%
- 1台障害時の想定

**ステップ1: 通常時の処理能力**
```
処理能力 = 1000 × 4 × 0.9
        = 3600リクエスト/秒
```

**ステップ2: 1台障害時の処理能力**
```
障害時処理能力 = 3600 × (3/4)
              = 2700リクエスト/秒
```

**結果: 1台障害でも75%の処理能力を維持**

💡 **実際の現場では**: ロードバランサーの設定（ラウンドロビン、最小接続数、重み付け）により性能が大きく変わります。また、セッション管理（スティッキーセッション、セッション共有）の方式により、システム設計が変わることに注意が必要です。

### ホットスタンバイシステム（Hot Standby System）
**特徴:**
- 待機系も起動状態を維持
- データはリアルタイムで同期
- 瞬時の切り替えが可能

**算出方法:**
```
切替時間 = 障害検知時間 + 切替処理時間（起動時間不要）
データ損失量 = 同期遅延時間 × データ流量
```

**📊 具体的な計算例**
**例: ECサイトのデータベースシステム**
- 障害検知時間: 5秒
- 切替処理時間: 10秒
- 同期遅延時間: 100ms
- データ流量: 100トランザクション/秒

**ステップ1: 切替時間の計算**
```
切替時間 = 5秒 + 10秒
        = 15秒
```

**ステップ2: データ損失量の計算**
```
データ損失量 = 0.1秒 × 100トランザクション/秒
            = 10トランザクション
```

**結果: 15秒で切り替え完了、最大10トランザクションの損失リスク**

💡 **実際の現場では**: 同期方式（同期レプリケーション、非同期レプリケーション）の選択が重要。同期レプリケーションは完全性を保証するが、ネットワーク遅延の影響を受けやすく、非同期は高速だがデータ損失のリスクがあります。

### コールドスタンバイシステム（Cold Standby System）
**特徴:**
- 待機系は停止状態
- 障害時に起動して処理を引き継ぐ
- コストは低いが切替時間が長い

**算出方法:**
```
切替時間 = 障害検知時間 + システム起動時間 + データ復旧時間 + 切替処理時間
運用コスト = アクティブ系コスト + (待機系コスト × 0.2〜0.3)
```

**📊 具体的な計算例**
**例: 社内業務システム**
- 障害検知時間: 5分
- システム起動時間: 10分
- データ復旧時間: 20分
- 切替処理時間: 5分

**ステップ1: 切替時間の計算**
```
切替時間 = 5分 + 10分 + 20分 + 5分
        = 40分
```

**ステップ2: 月間運用コストの計算（アクティブ系10万円/月の場合）**
```
運用コスト = 10万円 + (10万円 × 0.25)
          = 10万円 + 2.5万円
          = 12.5万円/月
```

**結果: 切替に40分必要だが、運用コストは25%増で済む**

💡 **実際の現場では**: バックアップからの復旧手順を詳細に文書化し、定期的な復旧訓練が必須です。また、待機系の定期的な起動確認（月次など）を行い、いざという時に起動しないリスクを低減する必要があります。

### デュプレックスシステムとホットスタンバイシステムの関係

**共通点:**
両者とも**主系（現用系）と待機系の2系統**で構成される冗長化方式です。通常時は主系が処理を行い、障害時に待機系に切り替わる点で基本的な構造は同じです。

**主な違い:**

#### 待機系の状態
- **デュプレックスシステム**: 待機系は「スタンバイ状態」（必要最小限の待機状態）
- **ホットスタンバイシステム**: 待機系も「起動状態を維持」（完全に稼働状態）

#### データ同期
- **デュプレックスシステム**: データ同期方式は様々（リアルタイム/バッチなど選択可）
- **ホットスタンバイシステム**: データは**リアルタイムで同期**が前提

#### 切替時間
- **デュプレックスシステム**: 
  ```
  切替時間 = 障害検知時間 + 切替処理時間 + システム起動時間
  ```
- **ホットスタンバイシステム**: 
  ```
  切替時間 = 障害検知時間 + 切替処理時間（起動時間不要）
  ```

**関係性の整理:**
**ホットスタンバイは、デュプレックスシステムの一種**と考えることができます。デュプレックスシステムという大きな分類の中で、待機系を常に起動状態に保ち、データをリアルタイム同期することで、より高速な切り替えを実現したものがホットスタンバイシステムです。

資料内の例では：
- デュプレックスシステム：切替に210秒（約3.5分）
- ホットスタンバイシステム：切替に15秒

この違いは、待機系の起動時間（120秒）が不要になることによるものです。

## 3. 詳細仕様・パラメータ

### 重要な設計パラメータ

#### フェイルオーバー時間（Failover Time）
- **意味**: 障害検知から切替完了までの時間
- **設定範囲**: 数秒〜数十分
- **影響**: ビジネス継続性、ユーザー体験
- **推奨値**: 
  - ミッションクリティカル: 10秒以内
  - 基幹系: 1分以内
  - 情報系: 5分以内

#### データ同期方式（Data Synchronization Method）
- **意味**: 主系と待機系のデータ同期方法
- **設定範囲**: 
  - 同期レプリケーション
  - 非同期レプリケーション
  - 定期バックアップ
- **影響**: データ整合性、性能、ネットワーク負荷
- **推奨値**: RPOに応じて選択

#### 健全性監視間隔（Health Check Interval）
- **意味**: システムの正常性を確認する間隔
- **設定範囲**: 1秒〜5分
- **影響**: 障害検知の迅速性、システム負荷
- **推奨値**: 
  - リアルタイム系: 1〜5秒
  - オンライン系: 10〜30秒
  - バッチ系: 1〜5分

#### 切替判定閾値（Failover Threshold）
- **意味**: 切替を実行する判定基準
- **設定範囲**: 
  - 応答時間超過回数
  - エラー率
  - リソース使用率
- **影響**: 誤切替の頻度、障害検知の確実性
- **推奨値**: 3回連続エラーまたは30秒無応答

## 5. メリット・デメリット

### メリット

**1. 高可用性の実現**
- **理由**: 単一障害点の排除により、システム全体の停止を防ぐ
- **効果**: ビジネス継続性の確保、サービスレベルの向上
- **具体例**: 銀行ATMでの99.999%稼働率実現

**2. 無停止メンテナンス**
- **理由**: 片系ずつメンテナンスすることで、サービスを継続
- **効果**: 計画停止の削減、メンテナンスの柔軟性向上
- **具体例**: OSパッチ適用を営業時間中に実施可能

**3. 処理能力の向上**
- **理由**: 複数システムでの負荷分散により、全体性能が向上
- **効果**: レスポンスタイム短縮、同時処理数の増加
- **具体例**: Webサーバー4台構成で3.6倍の処理能力

**4. 災害対策**
- **理由**: 地理的に分散配置することで、局所災害の影響を回避
- **効果**: 事業継続性の確保、コンプライアンス対応
- **具体例**: 東日本と西日本でのサイト分散

### デメリット

**1. 導入・運用コストの増大**
- **理由**: ハードウェア、ソフトウェア、ネットワークの重複投資
- **影響**: 初期投資2〜3倍、運用コスト1.5〜2倍
- **対策**: クラウドサービスの活用、仮想化技術の導入

**2. システムの複雑化**
- **理由**: 同期処理、切替制御、監視機能の追加
- **影響**: 設計難易度上昇、トラブルシューティングの困難化
- **対策**: 自動化ツールの活用、運用手順の標準化

**3. データ整合性の課題**
- **理由**: 複数システム間でのデータ同期タイミングのずれ
- **影響**: 一時的なデータ不整合、トランザクション管理の複雑化
- **対策**: 分散トランザクション管理、イベントソーシングの採用

**4. 誤切替のリスク**
- **理由**: ネットワーク瞬断等による誤検知
- **影響**: 不要な切替によるサービス瞬断、データ不整合
- **対策**: 適切な監視閾値設定、切替判定の多重化

### 適用判断フローチャート
1. **RPO（目標復旧時点）は0か？**
   - Yes → デュアルシステムまたは同期レプリケーション付きホットスタンバイ
   - No → 次の判断へ

2. **RTO（目標復旧時間）は1分以内か？**
   - Yes → ロードシェアシステムまたはホットスタンバイ
   - No → 次の判断へ

3. **コスト制約は厳しいか？**
   - Yes → コールドスタンバイまたはクラウド活用
   - No → デュプレックスシステムまたはホットスタンバイ

4. **負荷変動は大きいか？**
   - Yes → ロードシェアシステム（オートスケーリング対応）
   - No → 要件に応じた最適な方式を選択

## 9. 専門用語集

このスライドで使用された技術用語について、アルファベット順・50音順で解説します。

### アルファベット

**Chaos Engineering（カオスエンジニアリング）**
- **読み方**: カオスエンジニアリング
- **意味**: 本番環境に意図的に障害を注入してシステムの耐障害性を検証する手法。Netflixが提唱し、Chaos Monkeyというツールで有名
- **関連用語**: Fault Injection（障害注入）、Resilience Testing（耐障害性テスト）

**Failover（フェイルオーバー）**
- **読み方**: フェイルオーバー
- **意味**: 現用系システムに障害が発生した際に、待機系システムに自動的に切り替える機能や処理
- **関連用語**: Failback（フェイルバック）、Switchover（スイッチオーバー）

**HA（High Availability）**
- **読み方**: エイチエー、ハイアベイラビリティ
- **意味**: 高可用性。システムが長時間連続して稼働できる能力。通常99.9%以上の稼働率を指す
- **関連用語**: Availability（可用性）、Uptime（稼働時間）

**Health Check（ヘルスチェック）**
- **読み方**: ヘルスチェック
- **意味**: システムやサービスの正常性を定期的に確認する監視機能
- **関連用語**: Monitoring（監視）、Heartbeat（ハートビート）

**Load Balancer（ロードバランサー）**
- **読み方**: ロードバランサー
- **意味**: 複数のサーバーに負荷を分散する装置やソフトウェア。HAProxyやNginxが代表例
- **関連用語**: Load Distribution（負荷分散）、Traffic Distribution（トラフィック分配）

**RPO（Recovery Point Objective）**
- **読み方**: アールピーオー
- **意味**: 目標復旧時点。障害発生時にどの時点までのデータを復旧するかの目標値
- **関連用語**: Data Loss（データ損失）、Backup Window（バックアップウィンドウ）

**RTO（Recovery Time Objective）**
- **読み方**: アールティーオー
- **意味**: 目標復旧時間。障害発生からサービス復旧までの目標時間
- **関連用語**: Downtime（ダウンタイム）、MTTR（平均復旧時間）

**Service Mesh（サービスメッシュ）**
- **読み方**: サービスメッシュ
- **意味**: マイクロサービス間の通信を管理・制御するインフラストラクチャ層。Istioが代表例
- **関連用語**: Microservices（マイクロサービス）、Sidecar Proxy（サイドカープロキシ）

**SPOF（Single Point of Failure）**
- **読み方**: エスポフ、シングルポイントオブフェイラー
- **意味**: 単一障害点。そこが故障するとシステム全体が停止する箇所
- **関連用語**: Redundancy（冗長性）、Fault Tolerance（耐障害性）

**Streaming Replication（ストリーミングレプリケーション）**
- **読み方**: ストリーミングレプリケーション
- **意味**: データベースの更新をリアルタイムで他のデータベースに複製する技術
- **関連用語**: WAL（Write Ahead Log）、Logical Replication（論理レプリケーション）

### あ行

**オートスケーリング（Auto Scaling）**
- **読み方**: オートスケーリング
- **意味**: システムの負荷に応じて、サーバー台数を自動的に増減させる機能
- **関連用語**: スケールアウト、スケールイン、弾力性（Elasticity）

### か行

**稼働率（Availability Rate）**
- **読み方**: かどうりつ
- **意味**: システムが正常に稼働している時間の割合。(稼働時間÷全時間)×100で計算
- **関連用語**: ダウンタイム、MTBF（平均故障間隔）、MTTR（平均復旧時間）

**可用性（Availability）**
- **読み方**: かようせい
- **意味**: システムが継続して稼働できる能力。耐障害性と保守性を含む概念
- **関連用語**: 信頼性（Reliability）、保守性（Maintainability）

**クラスタリング（Clustering）**
- **読み方**: クラスタリング
- **意味**: 複数のコンピュータを連携させて1つのシステムとして動作させる技術
- **関連用語**: ノード（Node）、クラスタマネージャー

**コールドスタンバイ（Cold Standby）**
- **読み方**: コールドスタンバイ
- **意味**: 待機系システムが停止状態で待機する冗長化方式
- **関連用語**: ホットスタンバイ、ウォームスタンバイ

### さ行

**冗長化（Redundancy）**
- **読み方**: じょうちょうか
- **意味**: システムやコンポーネントを複数用意して信頼性を向上させること
- **関連用語**: 二重化、多重化、冗長性

**スイッチオーバー（Switchover）**
- **読み方**: スイッチオーバー
- **意味**: 計画的にシステムを切り替える操作。フェイルオーバーと異なり手動で実施
- **関連用語**: フェイルオーバー、切り戻し（Switchback）

**スティッキーセッション（Sticky Session）**
- **読み方**: スティッキーセッション
- **意味**: 同一クライアントからのリクエストを同じサーバーに振り分ける負荷分散方式
- **関連用語**: セッションアフィニティ、セッション維持

**ストレージレプリケーション（Storage Replication）**
- **読み方**: ストレージレプリケーション
- **意味**: ストレージレベルでデータを複製する技術
- **関連用語**: 同期複製、非同期複製、ミラーリング

### た行

**耐障害性（Fault Tolerance）**
- **読み方**: たいしょうがいせい
- **意味**: システムの一部に障害が発生しても全体として正常に動作し続ける能力
- **関連用語**: フォールトトレラント、障害耐性、レジリエンス

**デュアルシステム（Dual System）**
- **読み方**: デュアルシステム
- **意味**: 2つのシステムが同時に同じ処理を実行し、結果を照合する冗長化方式
- **関連用語**: 二重系、照合システム

**デュプレックスシステム（Duplex System）**
- **読み方**: デュプレックスシステム
- **意味**: 主系と待機系の2系統で構成される冗長化方式
- **関連用語**: 現用系・待機系、アクティブ・スタンバイ

**同期レプリケーション（Synchronous Replication）**
- **読み方**: どうきレプリケーション
- **意味**: データの書き込みが全てのレプリカで完了してから応答を返す複製方式
- **関連用語**: 非同期レプリケーション、準同期レプリケーション

### な行

**二重化（Duplication）**
- **読み方**: にじゅうか
- **意味**: システムやコンポーネントを2つ用意して冗長性を持たせること
- **関連用語**: 冗長化、多重化、ミラーリング

### は行

**ハートビート（Heartbeat）**
- **読み方**: ハートビート
- **意味**: システム間で定期的に送受信される生存確認信号
- **関連用語**: キープアライブ、死活監視、ヘルスチェック

**非同期レプリケーション（Asynchronous Replication）**
- **読み方**: ひどうきレプリケーション
- **意味**: データの書き込み完了を待たずに応答を返す複製方式
- **関連用語**: 同期レプリケーション、遅延レプリケーション

**フェイルバック（Failback）**
- **読み方**: フェイルバック
- **意味**: 障害復旧後、待機系から主系に処理を戻す操作
- **関連用語**: フェイルオーバー、切り戻し

**負荷分散（Load Balancing）**
- **読み方**: ふかぶんさん
- **意味**: 複数のサーバーやリソースに処理を分配して負荷を平準化すること
- **関連用語**: ロードバランシング、トラフィック分散

**ホットスタンバイ（Hot Standby）**
- **読み方**: ホットスタンバイ
- **意味**: 待機系システムが起動状態で待機する冗長化方式
- **関連用語**: コールドスタンバイ、ウォームスタンバイ

### ま行

**ミラーリング（Mirroring）**
- **読み方**: ミラーリング
- **意味**: データを複数の記憶装置に同時に書き込む技術
- **関連用語**: RAID1、ディスクミラー、複製

**無停止運用（Non-stop Operation）**
- **読み方**: むていしうんよう
- **意味**: システムを停止させることなく継続的に運用すること
- **関連用語**: 24時間365日運用、連続稼働

### ら行

**ラウンドロビン（Round Robin）**
- **読み方**: ラウンドロビン
- **意味**: 順番に均等に処理を割り当てる負荷分散方式
- **関連用語**: 輪番方式、循環方式

**レプリケーション（Replication）**
- **読み方**: レプリケーション
- **意味**: データを複数の場所に複製する技術
- **関連用語**: 複製、データ同期、ミラーリング

**ロードシェアシステム（Load Share System）**
- **読み方**: ロードシェアシステム
- **意味**: 複数のシステムで負荷を分担して処理する冗長化方式
- **関連用語**: 負荷分散システム、並列処理システム
